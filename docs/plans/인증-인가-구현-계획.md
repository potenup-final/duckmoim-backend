# 인증·인가 구현 계획 (auth · identity)

`AU-01` ~ `AU-07` · `AD-06` 을 **티켓 다섯 장**으로 끊은 실행 계획이다.

**이 문서의 자리** — 위키는 *무엇을 왜 만드는가*(설계·컨벤션), 이 문서는 *어떤 순서로
만드는가*(실행)다. 요구사항 원문·불변식·에러 코드는 여기 옮겨 적지 않는다. 위키가 정본이고,
여기에는 **위키만 봐서는 알 수 없는 것** — 티켓 경계, 순서의 근거, 남과 물린 지점 — 만 둔다.

## 2. 순서의 근거

### ① 계약은 되돌리기가 가장 비싸다 → A 를 맨 앞으로

`AuthUser` 는 **모든 도메인의 컨트롤러가 참조하는 계약**이다. 소희·슬기가 쓰기 시작한 뒤에
모양을 바꾸면 남의 코드를 고쳐야 한다. A 가 만드는 것은 뼈대지만 **정하는 것은 계약이다.**

### ② 남의 막힘 — 같은 결론, 다른 이유

CM-04 열람 권한의 판정 입력은 넷이다 — `(요청자, 방장, 댓글 작성자, 부모 댓글 작성자)`.
**「요청자」를 못 꺼내면 Comment 컨텍스트는 시작조차 못 한다.** 그리고 `develop` 에
머지돼야 한다 — 내 브랜치에 있으면 소용이 없다.

### ③ 검증 기준이 의존 방향을 정한다 → B → C → D

| 요구사항 | 검증 기준이 먼저 요구하는 것 | 그래서 |
| --- | --- | --- |
| AU-04 | 필터가 `tokens_invalidated_at` 을 읽는다 | **B 가 필터를 DB 에 연결한다** |
| AU-06 | **DB 유니크 제약 위반**을 409 로 변환한다 | 저장소 정본이 선 뒤 = **B 뒤** |
| AU-07 | `status` 를 `ACTIVE` 로 바꿔본 유저가 있다 | **C 뒤** |

**AU-02·03·04 를 쪼개지 않는 이유** — AU-03 의 「유저 전체 폐기」와 AU-04 의 「즉시 차단」이
`tokens_invalidated_at` **한 줄로 같이 처리된다.** 쪼개면 뒤 티켓이 세 줄짜리가 된다.

**C 가 D 보다 먼저인 이유** — `status` 를 `ACTIVE` 로 바꾸는 유일한 경로가 C 다.
**쓰는 쪽이 읽는 쪽보다 먼저 있어야** D 의 통합 테스트가 픽스처로 값을 직접 박지 않는다.

### ④ 외부 의존은 뒤로 → E 를 맨 끝으로

E 는 카카오 콘솔 등록이 끝나야 시작된다. **통제할 수 없는 일**이라 B·C·D 에 묶으면
그것들이 같이 대기한다. 콘솔이 일찍 열리면 **C 앞으로 당겨도 된다** — E 는 B 만 있으면 된다.
단, E 만으로는 여정이 닫히지 않는다. 로그인은 되는데 가입을 완료할 방법이 없다.

### 대기 구간은 억지로 채우지 않는다

A 가 끝나고 STAR-40 이 오기 전까지 빈 구간이 생긴다. 여기에 「운영 환경 시크릿 배선」
티켓을 넣었다가 **뺐다** — RDS 가 없어 완료 판정(prod 기동)을 만족할 수 없고, 카카오
시크릿은 콘솔 등록 전까지 값 자체가 없다. **완료할 수 없는 일을 대기 구간에 넣으면
순서를 만든 게 아니라 만든 척한 것이다.** 그 시간에 할 일은 소희와 `user` 컬럼을
맞추는 것이고, 그건 티켓이 아니라 합의다.

## 3. 패키지 배치

`auth` 와 `identity` 를 **같은 층위의 최상위 도메인**으로 둔다. 아키텍처 컨벤션의
「도메인을 최상위 기준으로 나누고 내부를 네 레이어로」를 그대로 따른다.

```
com.duckmoim
├── auth                          ← 인증 전부. 토큰과 관문
│   ├── domain        AuthUser · TokenPair · RefreshToken
│   │                 TokenProvider · RefreshTokenRepository          ← 포트(인터페이스)
│   │                 RefreshTokenValidator · RefreshTokenRotator     ← 도메인 서비스 (B)
│   ├── service       AuthService(발급·회전·로그아웃) · AuthenticationService (B)
│   ├── infra         JwtProvider · RefreshTokenJpaRepository         ← 포트 구현
│   ├── presentation  AuthenticationFilter · SecurityConfig · AuthAuthority
│   │                 AuthController · 에러 응답기
│   └── exception     AuthErrorCode
│
└── identity                      ← 회원. 가입 정보와 프로필
    ├── domain        User · SignupStatus · SignupInfo · BirthYear
    ├── service       SignupService · UserQueryService
    ├── infra         UserRepository
    ├── presentation  UserController
    └── exception     UserErrorCode
```

**`TokenClaims` 를 따로 두지 않는다.** 「토큰에 든 것」과 「인증 주체」가 우리에선 필드가
완전히 같아서(`userId` · `signupCompleted` · `admin`) 두 record 가 글자까지 똑같아진다. 값이
갈리는 날 나눈다.

**토큰에 관한 것을 전부 `auth` 에 모은다.** 발급·회전·검증·관문이 한 도메인 안에서 끝나고,
`identity` 는 순수하게 회원만 다룬다. 관문에만 갇힌 얇은 `auth` 를 만들면 토큰 로직이
`identity` 로 흩어져 「인증을 고치려면 어디를 봐야 하나」가 갈라진다.

**`identity` 와 `admin` 은 STAR-40 이 먼저 세운다.** `identity.domain.User` · `SignupStatus` ·
`identity.infra.UserRepository` · `admin.domain.AdminAccount` ·
`admin.infra.AdminAccountRepository` 가 그 PR 로 들어온다. 위 트리에서 내가 새로 만드는 것은
**`auth` 전부와 `identity` 의 나머지**다.

**빈 패키지를 미리 만들지 않는다.** 파일이 생기는 순간 디렉터리도 생긴다. 레이어별 규칙은
`.claude/rules/{domain,service,infra,presentation}.md` 가 해당 경로에서 자동으로 주입하므로
`package-info.java` 에 같은 내용을 두면 정본이 갈라진다.

### 레이어 이름은 `service` 다 — `application` 이 아니다

ArchUnit 이 `..presentation..` · `..service..` · `..domain..` · `..infra..` **네 이름으로만**
레이어를 가른다. `application` 으로 두면 그 패키지가 레이어로 인식되지 않아
**의존성 검사가 통째로 무력화된다.** 같은 이유로 `SecurityConfig` 를 `auth/config` 가 아니라
`presentation` 에 둔다 — 등급 매트릭스를 담은 가장 중요한 파일을 규칙 밖에 둘 이유가 없다.
`common.auth` 를 쓰지 않는 이유도 같다.

### 에러 코드는 `domain` 이 아니라 `exception` 에 둔다

`ErrorCode` 인터페이스가 `HttpStatus getStatus()` 를 요구한다. 구현 enum 은 `HttpStatus` 필드를
갖게 되고, 그것을 `..domain..` 에 두면 **`DOMAIN_IS_FRAMEWORK_FREE` 가 막는다** — domain 은
Spring 을 참조하지 않는다.

자리는 STAR-30 이 이미 정했다 — **`com.duckmoim.{도메인}.exception.{도메인}ErrorCode`**.
`common.exception` 과 대칭이고 레이어 이름이 아니라 게이트의 판정 대상이 아니다.
API 컨벤션의 「도메인별 enum, 중앙 집중 enum 없음」도 같은 배치를 가리킨다.

### 위키 컨텍스트 맵과 어긋나지 않는가

도메인 모델링 2장은 `AuthSession` 을 Identity 컨텍스트 안에 뒀다. **패키지 분리와 바운디드
컨텍스트는 다른 층위다** — 컨텍스트는 그대로 Identity 하나이고, 그 안을 「토큰」과 「회원」
두 패키지로 나눈 것뿐이다. 위키를 고칠 필요가 없다.

### 지켜야 하는 의존 방향

```
companion.presentation ─┐
comment.presentation   ─┼──▶ auth.domain.AuthUser        ← 남의 도메인은 이것만 안다
admin.presentation     ─┘

                          ┌──▶ identity.service   (가입 완료 여부 · 제재 상태)
auth.presentation ──▶ auth.service
                          └──▶ admin              (관리자 화이트리스트 · D 티켓)
```

**어느 레이어도 `infra` 를 직접 부르지 않는다.** `LAYER_DEPENDENCY` 의
`whereLayer("infra").mayNotBeAccessedByAnyLayer()` 가 막는다. 그래서 토큰 기술은
**포트와 구현으로 갈린다.**

```
auth.presentation.AuthenticationFilter
        │  주입받는 타입
        ▼
auth.domain.TokenProvider          ← 인터페이스. jjwt 를 모른다
        ▲ implements
auth.infra.JwtProvider             ← jjwt 를 아는 유일한 클래스. Spring 이 꽂아준다
```

**A 에는 `auth.service` 가 없다.** 서명·만료만 보면 되고 그건 판정이 아니라 검증이라
필터가 포트를 바로 부른다. `AuthenticationService` 는 **B 에서 생긴다** — 그때 필터가
`tokens_invalidated_at` 을 DB 로 확인해야 하고, 그것이 service 의 일이다.

아키텍처 컨벤션의 service 절이 「`infra` 저장소 주입」을 허용한다고 적은 것이 이것이다 —
주입되는 **타입은 domain 의 인터페이스**이고 인스턴스만 infra 것이다. 컴파일 시점 의존은
domain 을 향하므로 게이트가 통과시킨다.

1. **남의 도메인은 `auth.domain.AuthUser` 하나만 참조한다.** 값 객체를 참조하는
   `presentation → domain` 이라 컨벤션이 허용하는 방향이다.
2. **`AuthUser` 는 Spring 을 참조하지 않는다.** 순수 record 로 두고 필터가 `Authentication` 의
   principal 로 넣는다. `@AuthenticationPrincipal` 은 타입을 가리지 않는다.
3. **`auth.service → identity.service` 는 도메인을 넘는 참조다.** 아키텍처 컨벤션이 PR 합의를
   요구하는 대상이고, 이 문서가 그 합의다. `auth` 는 `identity.domain` 의 `User` 엔티티를
   직접 만지지 않고 **결과 객체만 받는다.**
4. **`admin` 참조는 D 티켓에서 슬기님과 합의한다.** STAR-40 이 `admin.domain.AdminAccount` 와
   `admin.infra.AdminAccountRepository.existsByKakaoUserId` 를 이미 만들었다. 저장소를 직접
   주입하면 **도메인을 넘는 `infra` 참조**가 되므로, `admin` 쪽에 판정 서비스를 두고 그것을
   부르는 쪽이 맞는지 D 티켓 PR 에서 정한다.

**게이트가 이 배치를 판정한다.** 네 레이어 이름을 그대로 쓰므로 `LAYER_DEPENDENCY` ·
`DOMAIN_REFERENCES_NOTHING` · `DOMAIN_IS_FRAMEWORK_FREE` 가 전부 적용된다.

### `presentation` 아래 하위 폴더는 파일이 늘면 만든다

`..presentation..` 이 하위까지 매칭하므로 `dto/` · `filter/` 로 나눠도 게이트가 유지된다.
처음부터 만들지는 않는다.

## 4. 티켓별 상세

### A — `chore: 공통 인증·인가 관문 구축`

| | |
| --- | --- |
| 담는 것 | Spring Security 세팅 · **`AuthUser` 계약** · 권한 등급 매트릭스 · 401·403 을 공통 에러 봉투로 · CORS · local 전용 개발 토큰 · `@WithAuthUser` 픽스처 |
| 검증 | 4등급 × 4상태 전 조합. **선언하지 않은 경로는 401** |
| DB | 쓰지 않는다. 등급은 **토큰 클레임으로 판정한다** |

- **등급 매트릭스에 API 설계 2장의 전 엔드포인트를 선언한다.** 내 것만 넣으면 소희·슬기가
  컨트롤러를 붙이는 순간 401 이 난다.
- `JWT_SECRET` — local·test 는 기본값, **prod 는 기본값 없이 필수**로 건다. 기본값을 남기면
  기본 시크릿으로 배포되는 사고가 난다. 대신 `OpenApiDisabledInProdTest` 에 더미를 주입한다
  — 그 테스트가 prod 프로파일로 컨텍스트를 띄운다.
- **세션이 생기는 경로 넷을 전부 막는다.** `SessionCreationPolicy.STATELESS` 하나로는 부족하다
  — 그것은 `SecurityContextRepository` 만 막고, 기본 `HttpSessionRequestCache` 는 **인증 실패
  때마다 원래 요청을 세션에 저장해 `JSESSIONID` 를 만든다.** `requestCache` 를 끄고 CSRF ·
  `formLogin` · `httpBasic` 도 함께 끈다. 쿠키를 배제한 ADR 0001 을 설정으로 뒷받침하는 자리다.
- **필터는 실패해도 응답을 쓰지 않는다.** 만료·위조를 만나면 인증을 세우지 않고
  요청 속성 `AuthenticationFilter.ERROR_CODE` 에 `AuthErrorCode` 만 남긴 채 통과시킨다.
  `AuthenticationEntryPoint` 가 그 값을 읽어 `AUTH_ACCESS_TOKEN_EXPIRED` 와
  `AUTH_ACCESS_TOKEN_INVALID` 를 가른다. **속성이 두 커밋 사이의 계약이다.**
- **필터에 `@Component` 를 붙이지 않는다.** 붙이면 Spring Boot 가 서블릿 필터로도 자동
  등록해 **요청마다 두 번 돈다.** `SecurityConfig` 가 `new` 로 만들어 체인에만 넣는다.
- **A 를 최종 상태로 두지 않는다.** 관리자 여부를 클레임으로 믿으므로 화이트리스트에서
  빼도 30분간 관리자다. D 가 그 구멍을 닫는다.

### B — `feat: AU-02 · AU-03 · AU-04 토큰 발급·재발급·로그아웃`

| | |
| --- | --- |
| 담는 것 | `RefreshToken` 도메인 · **`User` 스텁을 정본으로 확장** · 발급 · 회전 · 로그아웃 · **필터를 `user` 조회로 전환** |
| 검증 | AU-02 만료 Access 401 · AU-03 동일 Refresh 2회 → 두 번째 거부 + 세션 무효화 · AU-04 로그아웃 직후 401 |
| DB | **V12** — `refresh_token` 생성 + `user` 에 `tokens_invalidated_at` **ALTER** |

**테이블 이름은 `auth_session` 이 아니라 `refresh_token` 이다.** 애그리게이트 표가
「애그리게이트 `AuthSession` / **루트 `RefreshToken`**」으로 적었고, 엔티티와 테이블은 루트를
따른다. 그리고 이 표에 실제로 담기는 것은 **Refresh 토큰 해시 한 줄**이다 — Access 는 저장하지
않으므로 `auth_session` 은 담기지 않은 것까지 있는 것처럼 들리고, *"세션을 안 쓴다면서 왜 세션
테이블인가"* 를 매번 설명하게 된다.

> **우리는 stateless 가 아니다.** ADR 0001 이 정한 것은 「쿠키냐 헤더냐」이지 「상태를 갖느냐」가
> 아니다. Access 만 서명으로 검증하는 stateless 이고, **Refresh 는 AU-02 가 「서버 저장」을
> 명시했으며**(그래야 AU-03 재사용 탐지가 성립한다) 로그아웃은 AU-04 때문에 상태를 본다.
> **우리는 세션을 쓰지 않는다.** 요구사항이 「세션 무효화」(AU-03)라고 부르는 것은 서블릿
> 세션이 아니라 *그 유저의 로그인 상태*이고, 실제 동작은 **`refresh_token` 행 전부 삭제 +
> `tokens_invalidated_at` 갱신**이다. 그래서 메서드 이름도 세션을 쓰지 않는다 —
> **`invalidateAllTokens(userId)`**. `AuthSession` 은 위키의 애그리게이트 개념명으로만 남는다.

**`User` 에 실제로 더하는 것.** STAR-40 의 `User` 는 필드가 다 있고 **상태 전이 메서드가
하나도 없다.** 내가 붙이는 것은 셋이다.

- `tokensInvalidatedAt` 필드와 그 컬럼 (**V12 의 `ALTER TABLE user`**)
- 무효화 · `lastSeenAt` 갱신 상태 전이 메서드
- `UserRepository` 의 조회 메서드 — STAR-40 이 **의도적으로 비워 두었고**, 채우는 것은
  정본 담당인 내 몫이라고 그 PR 이 명시했다

**같은 파일을 두 사람이 건드린다.** STAR-40 이 먼저 머지되지 않으면 충돌한다.

**`tokens_invalidated_at` 은 요청하지 않고 내가 붙인다.** 도메인 3.1 의 `User` 애그리게이트
경계(SignupInfo · Profile · 계정 상태 · lastSeenAt)에 없고 `AuthSession` 애그리게이트 쪽 관심사라, STAR-40 이
안 넣은 것이 맞다. 다만 그 PR 본문이 *"실제로 붙일 것이 남아 있지 않기를 기대한다"* 고 적었으므로
**붙일 것이 하나 있다는 사실을 미리 알린다.** `refresh_token` 에 둘 수 없다 — 그 행을 전부 지운
뒤에는 비교할 행이 남지 않는다.

## 5. 확정된 계약

### 권한 등급이 판정되는 자리

등급을 **enum 으로 만들지 않는다.** Spring Security 가 이미 제공하는 것을 쓴다 — 필터가
클레임을 `GrantedAuthority` 로 바꿔 넣고, `SecurityConfig` 가 경로마다 요구 권한을 선언한다.

| 등급 | `SecurityConfig` 선언 | 위반 |
| --- | --- | --- |
| `PUBLIC` | `permitAll()` | — |
| `AUTH` | `authenticated()` | 401 |
| `SIGNUP` | `hasAuthority("SIGNUP")` | 403 |
| `ADMIN` | `hasAuthority("ADMIN")` — `/api/v1/admin/**` 한 줄 | 403 |
| `HOST` | **service 레이어. 관문이 제공하지 않는다** | 403 |

```java
// AuthenticationFilter — 클레임을 권한으로 옮긴다
List<GrantedAuthority> authorities = new ArrayList<>();
if (authUser.signupCompleted()) {
  authorities.add(new SimpleGrantedAuthority(AuthAuthority.SIGNUP));
}
if (authUser.admin()) {
  authorities.add(new SimpleGrantedAuthority(AuthAuthority.ADMIN));
}
```

**문자열은 `AuthAuthority` 상수로만 쓴다.** 필터와 `SecurityConfig` 두 곳에 같은 값이
들어가는데, 한쪽만 오타 나면 그 경로가 조용히 403 이 된다. 상수로 두면 최소한
**참조하는 자리**의 오타는 컴파일러가 잡는다.

**대가를 알고 고른 것이다.** 권한이 문자열이라 `hasAuthority("SINGUP")` 처럼 오타가 나도
컴파일이 통과하고, 그 경로는 **가입 완료한 사람에게도 조용히 403** 이 된다. 그래서 등급별
통합 테스트를 A 티켓의 완료 조건으로 둔다 — 오타는 그 테스트에서만 드러난다.

**401 과 403 은 Spring 이 가른다.** 익명이면 `AuthenticationEntryPoint`(401), 인증했는데
권한이 없으면 `AccessDeniedHandler`(403) 다. API 설계 1장의 「위반 시」 열과 그대로 맞는다.

**`HOST` 만 관문 밖이다.** 방장 여부는 그 모집글을 조회해야 판정된다. 모집글 수정·마감
API 를 만드는 쪽이 서비스에서 직접 판정한다 — 빠뜨리면 남의 글을 고칠 수 있다.

### 인증 필터는 막지 않는다

필터는 **신원만 확인하고, 막는 일은 등급 판정이 한다.** 토큰 없는 요청은 익명인 채로
통과해 등급 판정까지 간다. 이렇게 해야 PO-11(비인증 요청에도 본문 포함 200)과
CM-20(비회원 공개 댓글 열람)이 동시에 성립한다.

## 7. 함정

- **필터에서 난 401·403 은 `GlobalExceptionHandler` 를 지나지 않는다.** 필터가 컨트롤러
  앞에 서기 때문이다. 그냥 두면 STAR-30 이 만든 `{code, message}` 봉투가 깨진다 —
  `AuthenticationEntryPoint` · `AccessDeniedHandler` 로 직접 써야 한다.
- **Security 를 넣는 순간 기존 테스트가 깨진다.** `OpenApiExposureTest` ·
  `OpenApiDisabledInProdTest` · `HealthControllerTest` 가 401 을 받는다
  (`@WebMvcTest` 도 Security 자동설정을 포함한다). `GlobalExceptionHandlerTest` 는
  `standaloneSetup` 이라 안 깨진다. 그래서 **A 의 첫 커밋은 전 경로 `permitAll` 로 시작한다.**
- **`UnknownPathResponseTest` 와 정면 충돌한다.** 그 테스트가 *"없는 경로는 404
  `ENDPOINT_NOT_FOUND`"* 를 계약으로 못박았는데, 인증은 디스패처보다 먼저 돈다.
  `anyRequest().authenticated()` 로 가면 없는 경로도 401 이다. **401 쪽을 택하고
  PR 리뷰 포인트로 올린다** — 빠뜨림이 조용히 뚫리는 쪽보다 낫다.
- **`iat` 는 초 단위다.** `tokens_invalidated_at` 은 밀리초라, 로그아웃과 재로그인이 같은
  초에 일어나면 방금 받은 토큰이 죽거나 로그아웃이 안 먹는다. **부등호와 경계 테스트를
  반드시 쓴다.**
- **Rotation 의 정상 사용자 피해** — 재발급 응답을 못 받고 재시도하면 헌 Refresh 가 다시
  와서 로그아웃된다. AU-03 이 명시한 동작이라 그대로 가지만 CS 문의가 들어올 항목이다.
- **테이블명이 `user` 단수다** (STAR-40). MySQL 비예약 키워드라 동작하고 엔티티에
  `@Table(name = "user")` 가 이미 명시돼 있다.
- **`intro` 와 `bio` 가 갈렸다.** STAR-40 의 컬럼·필드는 `intro` 인데 API 설계 2-2 와 화면 계약은
  응답 필드를 **`bio`** 로 못박았다. API 컨벤션이 *"도메인 식별자와 API 필드명을 일치시킨다"* 이므로
  **C 티켓에서 `RENAME COLUMN` 으로 맞춘다** (V13). 안 적어 두면 매핑에서 조용히 갈라진다.
- **`V11__seed_user` 의 더미 7건과 `deleteAllInBatch` 가 충돌한다.** 그 회원들이 Flyway 로
  들어가 Testcontainers 통합 테스트에도 존재하는데, 테스트 컨벤션은 동시성 테스트에서
  *"`deleteAllInBatch()` 로 테이블을 비운다"* 고 한다. **비우면 뒤 테스트가 전제하던 더미가
  사라진다.** C 의 AU-06 동시성 테스트가 정확히 그 경우다 — 더미에 의존하지 않게 짜거나
  자기가 만든 행만 정리한다.

## 8. 이 계획 밖

빠뜨린 것이 아니라 **선행이 남의 컨텍스트에 달려 있어 나중에 끊는다.**

| ID | 요구사항 | 우선 | 왜 지금이 아닌가 |
| --- | --- | --- | --- |
| AU-09 | 공개 프로필 조회 | 필수 | `/users/{userId}/posts` 가 `CompanionPost` 를 읽는다. **프로필 단건은 의존이 없어 먼저 낼 수 있다** |
| AU-08 | 프로필 수정 | 권장 | 텍스트 수정은 의존이 없다. **이미지 업로드만** 스토리지 인프라를 기다린다 |
| AU-10 | 내 활동 내역 | 필수 | 모집글·댓글 **양쪽**을 읽는다. **CM-16 과 같은 요구사항이라 소유 합의가 먼저다** |
| AU-11 | 회원 탈퇴 | 선택 | 명세서에서 유일한 '선택'. API 설계도 *"1차에서 뺄 수 있다"* |
| AU-12 | 제재 안내 | 필수 | `Sanction` 이 있어야 성립한다. **Safety 담당 티켓에 붙인다** |

**AU-10 과 CM-16 은 같은 요구사항이다.** 비밀 댓글 본문을 내려주는 경로가 셋(목록 · 내 내역 ·
백오피스)인데 **판정 코드는 하나여야 한다**(도메인 7.1). 내 내역만 다른 담당이 만들면 그
하나가 갈라진다 — Identity 가 둘 다 만들고 Comment 담당은 조회 메서드만 여는 쪽을 제안한다.

Identity 담당 전체는 티켓 아홉 장이고, 이 문서의 다섯이 인증·인가다.
