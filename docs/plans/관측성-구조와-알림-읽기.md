### 왜 Grafana 와 CloudWatch 를 둘 다 쓰나

**보는 위치가 다르다.**

```
CloudWatch    AWS 자원을 「바깥에서」 본다
              ALB 가 5xx 를 뱉었나 · RDS 저장공간이 남았나
              → 서버 안쪽은 못 본다

Grafana       서버 「안에서」 본다
              디스크·메모리·CPU · 앱 로그 · 앱 지표
              → AWS 콘솔 정보는 못 본다
```

둘이 겹치지 않는다. 그래서 둘 다 있다.

## 2. 각 기술이 어디에 들어갔나

| 기술 | 역할 | 어디에 |
|---|---|---|
| **Spring Boot Actuator** | 앱이 자기 상태를 숫자로 내놓는 창구 | 앱 안. `/actuator/health` · `/actuator/prometheus` |
| **Micrometer** | Actuator 뒤에서 실제로 재는 계측기 | 앱 안. 힙·요청 수·DB 커넥션 |
| **Grafana Alloy** | 수집기. 서버에서 긁어 클라우드로 밀어보냄 | EC2 두 대에 systemd 서비스 |
| **Prometheus 형식** | 지표를 주고받는 표준 형식 | Alloy ↔ Grafana Cloud |
| **Loki** | 로그 저장소 | Grafana Cloud |
| **Grafana** | 대시보드 · 로그 검색 · 알림 규칙 | Grafana Cloud (웹) |
| **CloudWatch** | AWS 자원 지표와 알람 | AWS |
| **SNS + Amazon Q Developer** | CloudWatch 알람을 Slack 으로 옮기는 다리 | AWS |

> **프로메테우스 「서버」는 안 쓴다.** 형식만 쓰고, 저장은 Grafana Cloud 가 대신한다.
> EC2 를 추가할 수 없어서 내린 결정이다.

### Alloy 가 모으는 것 4가지

```
① 호스트 지표     CPU · 메모리 · 디스크 · 네트워크        job=integrations/node_exporter
② 시스템 로그     journald · /var/log/*.log            job=integrations/node_exporter
③ 앱 컨테이너 로그  docker logs duckmoim-app 과 같은 것   job=duckmoim/docker
④ 앱 지표        /actuator/prometheus                  job=duckmoim-backend
```

**③이 가장 자주 쓰게 될 것이다.** SSH 없이 앱 로그를 검색한다.

## 3. Slack 알림 3종 — 어디서 오고 어떻게 읽나

`#6-인프라-알림` 에는 **세 종류**가 온다. **보낸 사람 이름으로 구분한다.**

| 보낸 사람 | 무엇 | 언어 | 첫 글자 |
|---|---|---|---|
| `duckmoim-deploy` | 배포 성공/실패 | 한국어 | ✅ 🚨 ⚠️ |
| `Grafana` | 서버 이상 (디스크·메모리·수집 끊김) | 영어 틀 + 한국어 내용 | `[FIRING:n]` |
| `AWS Chatbot` / `Amazon Q` | AWS 자원 이상 (ALB·RDS) | 영어 | `ALARM:` |

> `Username` 설정이 빠진 것이다 (같은 Slack 앱의 웹훅을 쓰기 때문). 그때는 **첫 글자**로
> 가른다 — 배포 알림은 이모지로, Grafana 알림은 `[FIRING:n]` 으로 시작한다.

### 3-1. 배포 알림 — 보낸 사람 `duckmoim-deploy`

**어디서 오나** — GitHub Actions 의 `ci-cd.yml` 이 배포 잡 마지막에 Slack 웹훅을 부른다.
`main` 에 머지될 때마다 **성공이든 실패든** 온다.

```
✅ 배포 성공 — 현재 서비스: green

  커밋                          실행
  a3f9c21 fix: 헬스체크의 …      J-DONGHYUN

  [ 실행 로그 ]
```

**읽는 법**

| 부분 | 뜻 |
|---|---|
| `현재 서비스: green` | 지금 사용자 트래픽을 받는 서버. **리스너를 실제로 다시 읽어서 적은 값이다** |
| `커밋` | 무엇이 배포됐나 |
| `실행` | 누가 머지했나 |
| `실행 로그` | 누르면 GitHub Actions 로 간다 |

**실패 메시지는 네 가지 중 하나다.**

```
🚨 배포 실패 — 현재 서비스: blue (바뀌지 않음)
   리스너를 옮기지 않았거나 되돌렸다. 사용자 영향은 없다.
   → 배포만 실패. 서비스는 멀쩡하다. 급하지 않다

🚨 배포 실패 — 현재 서비스: green (새로 올린 색)
   되돌리기가 끝나지 않았을 수 있다. 지금 확인이 필요하다.
   → ⚠️ 위험. 바로 봐야 한다

🚨 배포 실패 — 현재 서비스: 확인 불가
   리스너 상태를 읽지 못했다. 사람이 직접 확인해야 한다.
   → AWS 자격증명 단계에서 멈췄을 가능성. 직접 확인

⚠️ 배포 취소 — 현재 서비스: blue
   → 사람이 중간에 끊은 것. 컨테이너와 리스너가 어긋났을 수 있다
```

> **왜 실패 알림이 더 중요한가.** 배포 게이트가 막으면 리스너가 안 움직이는 게 **올바른
> 동작**이라, 서비스에는 아무 흔적이 없다. 이 알림이 없으면 새벽에 멈춘 배포를 아무도 모른다.

### 3-2. Grafana 알림 — 보낸 사람 `Grafana`

**어디서 오나** — Grafana Cloud 가 1분마다 지표를 검사하고, 조건이 일정 시간 유지되면 보낸다.

영어 틀에 한국어 내용이 담겨 나온다. **틀만 알면 읽기 쉽다.**

```
[FIRING:1] EC2 디스크 사용률 85% 초과
Grafana

**Firing**

Value: C=87.3
Labels:
 - alertname = EC2 디스크 사용률 85% 초과
 - grafana_folder = duckmoim
 - instance = ip-172-31-35-164
Annotations:
 - summary = ip-172-31-35-164 루트 디스크 85% 초과. 6.6GB 볼륨이라 차면
             배포가 실패하고 로그도 못 쓴다. docker image prune 과
             ci-cd.yml 의 until=72h 를 확인한다.
Silence: https://sprypeony3107.grafana.net/alerting/silence/new?...
```

**한 줄씩 읽는 법**

| 영어 | 뜻 | 어떻게 쓰나 |
|---|---|---|
| `[FIRING:1]` | **지금 문제가 있다.** 뒤 숫자는 몇 건인지 | `1` 이면 한 서버, `2` 면 두 서버 다 |
| `[RESOLVED]` | **해결됐다.** 조건이 정상으로 돌아옴 | 이게 오면 상황 종료 |
| `Firing` / `Resolved` | 위와 같은 뜻의 본문 표시 | — |
| `Value:` | 조건을 넘긴 **실제 숫자** | `C=87.3` → 디스크가 87.3% |
| `Labels:` | **어느 서버·어떤 규칙**인지 | 아래 참고 |
| `alertname` | 규칙 이름 | 무슨 문제인지 |
| `instance` | **어느 서버인지** ← 가장 중요 | 6장의 대응표로 blue/green 확인 |
| (`instance` 가 없을 때) | 두 서버가 **같이** 울린 것 | `[FIRING:2]` 면 둘 다. 아래 참고 |
| `grafana_folder` | 규칙이 든 폴더 | 무시해도 된다 |
| `Annotations: summary` | **우리가 한국어로 적어둔 설명과 할 일** | 여기만 읽어도 대응이 된다 |
| `Silence:` | 이 알림을 일정 시간 끄는 링크 | 아는 상황일 때만. 함부로 누르지 않는다 |

**`[FIRING:2]` 일 때 `instance` 가 안 보이는 이유.** 두 서버가 같은 조건으로 동시에
울리면 Slack 이 한 건으로 묶고 **공통 라벨만** 표시한다. `instance` 는 서버마다 다르니
빠진다. 한 서버만 울리면 `[FIRING:1]` 과 함께 `instance` 가 나온다.

> **`summary` 만 읽어도 된다.** 무엇이 왜 문제이고 뭘 확인해야 하는지 한국어로 적어뒀다.
> 영어 줄들은 「어느 서버인지」와 「숫자가 얼마인지」를 확인할 때만 본다.

**규칙 3개**

| 규칙 | 조건 | 유지 시간 | 왜 |
|---|---|---|---|
| EC2 디스크 사용률 85% 초과 | 루트 디스크 > 85% | 5분 | 6.6GB 볼륨. 차면 배포 실패 + 로그 못 씀 |
| EC2 메모리 사용률 90% 초과 | 메모리 > 90% | 10분 | JVM 이 힙을 70%까지 쓰므로 85 는 정상 상태 |
| EC2 지표 수집 끊김 | `up < 1` **또는 데이터 없음** | 5분 | EC2 나 Alloy 가 죽음 |

> **세 번째가 특별하다.** 서버가 통째로 죽으면 지표가 `0` 이 되는 게 아니라 **아예 안 온다.**
> 그래서 「데이터 없음」도 이상 신호로 읽게 설정해뒀다.

### 3-3. CloudWatch 알람 — 보낸 사람 `AWS Chatbot` / `Amazon Q`

**어디서 오나** — CloudWatch 경보 → SNS 주제 `duckmoim-alert` → Amazon Q Developer → Slack.

카드 형태로 오고 **전부 영어다.**

```
🔴 ALARM: "ALB 5xx 알람"
   Account: 416121583617   Region: Asia Pacific (Seoul)

   Threshold Crossed: 1 out of the last 1 datapoints [7.0]
   was greater than the threshold (5.0).

   2026-09-10T12:34:56Z
```

**핵심 단어만 알면 된다.**

| 영어 | 뜻 |
|---|---|
| `ALARM` | 문제 발생 |
| `OK` | 정상 복귀 |
| `INSUFFICIENT_DATA` | 판단할 데이터가 없음. 대개 무시해도 된다 |
| `Threshold Crossed` | 임계값을 넘었다 |
| `[7.0] was greater than the threshold (5.0)` | **실제 7, 기준 5** → 넘었다 |

**알람 2개**

| 알람 | 무엇을 본다 | 오면 |
|---|---|---|
| ALB 5xx | 로드밸런서가 5분 안에 5xx 를 몇 개 뱉었나 | 사용자가 에러를 보고 있다. **가장 급하다** |
| RDS 저장공간 | DB 디스크 여유 | 차면 DB 가 멈춘다 |

## 4. 알림이 오면 — 대응 순서

### 급한 순서

```
1순위   🔴 ALB 5xx                      사용자가 지금 에러를 보고 있다
2순위   🚨 배포 실패 (새로 올린 색)        되돌리기가 안 끝났을 수 있다
3순위   🔴 EC2 지표 수집 끊김             서버가 죽었을 수 있다
4순위   🔴 RDS 저장공간                   차면 DB 가 멈춘다
5순위   🔴 EC2 디스크 · 메모리            여유가 있다. 당일 안에 처리
6순위   🚨 배포 실패 (바뀌지 않음)         서비스는 멀쩡. 다음 배포로 해결
```

### 공통 3단계

**① 서비스가 살아 있나 — 10초**

```
https://api.duckmoim.com/api/health
→ {"status":"UP"} 이면 서비스는 살아 있다
```

**② 어느 서버인가**

알림의 `instance` 를 6장 대응표에서 찾는다. **트래픽을 받는 쪽인지 유휴 쪽인지가
급한 정도를 가른다** — 유휴 서버 문제는 사용자에게 안 닿는다.

**③ 로그를 본다 — SSH 필요 없다**

```
https://sprypeony3107.grafana.net  →  Explore
데이터소스: grafanacloud-sprypeony3107-logs
```

```logql
{container="duckmoim-app"}
```

에러만 보려면:

```logql
{container="duckmoim-app"} |= "ERROR"
```

한 서버만 보려면:

```logql
{container="duckmoim-app", instance="ip-172-31-38-192"}
```

```promql
up{job="integrations/node_exporter"}          서버가 살아 있나 (1이면 정상)
```

## 6. 서버 이름 대응표

| 알림의 `instance` | 색 | EC2 이름 | 공인 IP | 대상 그룹 |
|---|---|---|---|---|

### 지금 어느 쪽이 서비스 중인가

**색은 배포마다 번갈아 바뀐다.** 확인하는 법 두 가지.

```
① Slack 의 마지막 배포 알림   「현재 서비스: green」
② AWS 콘솔                  EC2 → 로드 밸런서 → duckmoim-alb → [리스너 및 규칙]
```

> **유휴 서버에도 앱은 떠 있다.** ALB 가 트래픽을 안 보낼 뿐이다.
> 그래서 유휴 서버 로그에는 사용자 요청이 거의 없고, 5분마다 도는 마감 배치 로그만 보인다.

## 7. 감시하지 않는 것 — 알고 있어야 오해가 없다

| 감시 안 함 | 왜 |
|---|---|
| 앱 지표 (힙·요청 수·DB 커넥션) | 설정은 끝났고 **`main` 머지 뒤부터** 들어온다 |
| 분산 추적 (Zipkin·Tempo) | 서비스가 하나뿐이라 「어느 서비스에서 느려졌나」가 없다 |
| RDS 상세 쿼리 분석 | `db.t4g.micro` 가 Performance Insights 를 지원하지 않는다 |
| AWS 비용 알림 | 공용 계정이라 다른 팀 비용까지 잡힌다 |
| 프론트엔드 오류 | 백엔드 관측성 범위 밖 |

> **「못 한 것」이 아니라 「안 하기로 판단한 것」이다.** 근거가 있어서 뺐다.

## 9. 자주 나올 질문

**Q. 알림이 왔는데 아무것도 안 해도 되나?**
`summary` 를 읽고 4장의 순서대로 판단한다. **유휴 서버 문제는 사용자에게 안 닿는다.**

**Q. `[RESOLVED]` 가 오면 끝난 건가?**
조건이 정상으로 돌아왔다는 뜻이다. 다만 **왜 그랬는지**는 남는다 — 반복되면 원인을 봐야 한다.

**Q. Silence 링크를 눌러도 되나?**
아는 상황(작업 중이라 일부러 그런 것)일 때만. **모르는 알림을 끄면 그 뒤로 안 온다.**

**Q. 로그가 안 보인다.**
시간 범위를 넓혀본다(우측 상단). 유휴 서버는 요청이 없어 로그가 드물다.

**Q. 같은 알림이 두 번 온다.**
서버 두 대가 각각 보낸 것이다. `instance` 라벨이 다르면 정상이다.
