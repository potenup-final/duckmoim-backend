# 회원·프로필 구현 계획 (identity)

`AU-08` ~ `AU-11` 을 **티켓 네 장**으로 끊은 실행 계획이다.

**이 문서의 자리** — [인증·인가 구현 계획](인증-인가-구현-계획.md)의 8장 「이 계획 밖」이
목록으로만 적어 두었던 것들을 티켓으로 끊는다. 위키는 *무엇을 왜 만드는가*, 이 문서는
*어떤 순서로 만드는가*다. 요구사항 원문·불변식·에러 코드는 옮겨 적지 않는다.

회원·프로필이 F~I 다.

## 2. 순서의 근거

### ① AU-08 의 검증 기준이 AU-09 를 요구한다 → 둘을 합쳐 F 로

명세서 AU-08 의 검증 기준이 *「수정 후 **공개 프로필 반영**. 중복 닉네임으로 변경 시 409」*
다. **수정만 만들면 앞 절반을 검증할 방법이 없다** — `/users/me` 재조회로 대신할 수는 있지만
그것은 검증 기준에 적힌 것이 아니다.

거꾸로도 성립한다. 공개 프로필만 만들면 **값이 바뀌는 경로가 가입(C) 하나뿐**이라 조회가
최신을 보는지가 드러나지 않는다. 읽는 쪽과 쓰는 쪽이 같은 `user` 표 한 장이고 DB 변경이
양쪽 다 없어서, 나누면 티켓 경계만 생기고 검증은 반쪽이 된다.

### ② 남을 안 타는 것이 먼저다 → F

F 가 읽고 쓰는 것은 `user` 표 하나다. C 만 머지되면 **그날 시작할 수 있다.**
G 이후는 남이 무엇을 열어주느냐에 걸려 있어서, 앞에 두면 대기가 앞으로 온다.

### ③ 판정 코드가 하나여야 해서 G 가 늦다

`GET /users/me/comments` 는 **비밀 댓글 본문을 내려준다** (AU-10 · CM-16). 도메인 7.1 이
*"본문을 반환하는 경로가 목록·상세·내 활동 내역·백오피스로 여럿이고, 하나만 빠뜨리면
규칙이 무의미하다"* 고 정했다. **그 판정기는 STAR-56 이 이미 만들었다.**

여기서 `CommentVisibilityPolicy` 를 **다시 만들지 않는다.** G 의 일은 그것을 부르는
것이고, 부를 수 있는 자리에 있는지 확인하는 것이다 — 3장에 있다.

### ④ 조회 경로가 다 선 뒤라야 탈퇴가 검증된다 → H

AU-11 의 검증 기준이 *「탈퇴 후 댓글 자리표시자 전환」* 이고, 도메인 4장이 소프트 삭제를
*"조회 경로 전반에 필터 필요"* 라고 적었다. **필터를 검증하려면 필터가 걸릴 경로가 있어야
한다.** F(공개 프로필) · G(내역)가 그 경로다. 먼저 하면 나중에 생기는 경로마다 빠뜨렸는지를
다시 확인해야 한다.

### ⑤ 외부 대기 티켓은 letter 가 순서를 정하지 않는다 → I

I 는 스토리지 인프라가 서야 시작된다. **통제할 수 없는 일**이라 언제 열리느냐가 순서를
정한다 — 먼저 서면 F 바로 뒤로 당겨져도 된다. 인증·인가 계획 2장이 *"완료할 수 없는 일을
대기 구간에 넣으면 순서를 만든 게 아니라 만든 척한 것이다"* 라고 적은 것과 같은 이유로,
대기 중인 I 를 실행 가능한 H 앞에 두지 않는다.

### 합치지 않은 것 둘 — 근거

**AU-08 을 F 와 I 로 쪼갰다.** API 설계가 이미 엔드포인트를 갈라 놨고
(`PATCH /users/me/profile` · `POST /users/me/profile-image`), 계약이 둘이라 쪼개도 깨지는
것이 없다. 붙여 두면 **의존이 없는 텍스트 수정이 스토리지를 같이 기다린다** — 그러면 ①의
검증 기준 전부가 함께 선다. 그리고 I 는 1차의 유일한 파일 업로드라 멀티파트·용량 제한·
MIME 검증·자격증명이 한꺼번에 들어온다. 다른 성질의 일이다.

**탈퇴(H)를 F 나 G 에 붙이지 않았다.** 명세서에서 유일한 '선택' 이고 API 설계도 *"1차에서
뺄 수 있다"* 고 적었다. **붙이면 뺄 수 없다.** 선택 항목이 필수 티켓 안에 들어가면 일정이
밀릴 때 잘라낼 자리가 사라진다.

## 3. 패키지 배치

인증·인가 계획 3장의 트리를 그대로 잇는다. **`auth` 는 건드리지 않는다.**

```
com.duckmoim.identity
├── domain        User · SignupStatus · SignupInfo · BirthYear      ← STAR-40 · C
│                 Profile (닉네임 · bio · 이미지 URL)                 ← F
│                 LastSeen (구간 값 · 도메인 7.2)                     ← STAR-57 이 만들었다
│                 ProfileImagePolicy · ProfileImageStorage(포트)     ← I
├── service       UserService · UserQueryService                    ← C · **F 가 여기에 더했다**
│                 PublicProfile · ProfileUpdateCommand              ← F
│                 MyActivityService · WithdrawService               ← G · H (예정)
├── infra         UserRepository                                    ← STAR-40 · C
│                 S3ProfileImageStorage · Stub… · S3Config          ← I
├── presentation  UserController · dto/                             ← C · F
└── exception     UserErrorCode                                     ← STAR-40
```

### `LastSeen` 은 이미 있다 — 전부 재사용한다

도메인 7.2 가 *"본인 조회(`/me`)에서도 동일하게 구간으로 내린다. 경로마다 형태가 다르면
조립 지점이 갈라진다"* 고 못박았다. **`lastSeen` 이 실리는 응답이 넷이다.**

| 응답 | 티켓 |
| --- | --- |
| 댓글 작성자 블록 (`CommentAuthorResponse`) | **슬기 · STAR-57 이 만들었다** |
| `GET /users/me` | C |
| `GET /users/{userId}` (공개 프로필) | F |
| 모집글 작성자 블록 | 박호빈 |

**이 계획은 「C 가 만들고 나머지가 부른다」로 적혀 있었는데 순서가 반대로 갔다.** 댓글 목록이
먼저 필요해져 **STAR-57 이 `identity/domain/LastSeen.java` 에 만들었다.** 자리는 계획대로
`identity.domain` 이고 — 7.2 가 회원 쪽에 두라고 정했다 — 그 파일 javadoc 이
*"AU-09 담당이 이어서 쓴다"* 고 넘겨 뒀다. **F·G 도, C 도 부르기만 한다.**

### `Profile` 값 객체를 F 에서 만든다

지금 `User` 는 `nickname` · `intro` · `profileImageUrl` 을 **필드 셋으로 평평하게** 갖고 있다
(STAR-40). 도메인 3.1 의 `User` 애그리게이트 경계는 `SignupInfo` 와 `Profile` 을 나눠 놨고,
**둘의 수정 규칙이 다르다** — 출생연도는 가입 후 잠기고(AU-08) 닉네임은 양쪽에 걸친다.

F 가 그 경계를 코드로 세운다. C 가 만든 `SignupInfo` 와 대칭이다.

## 4. 티켓별 상세

### F — `feat: AU-08 · AU-09 프로필 수정과 공개 프로필`

| | |
| --- | --- |
| 담는 것 | `Profile` 값 객체 · `PATCH /api/v1/users/me/profile` · `GET /api/v1/users/{userId}` · 닉네임 중복 409 재사용 · `LastSeen` **재사용** |
| 검증 | **수정 후 공개 프로필에 반영** · 중복 닉네임 409 · **출생연도를 보내도 바뀌지 않는다** · 가입 미완료 403 · 노출 항목 넷 그대로 · **출생연도가 응답에 없다** · 구간 경계 다섯 |
| DB | **없다.** 컬럼은 V10 에 다 있고 `intro → bio` 는 C 의 V14 가 끝낸다 |

**쓰는 쪽 (AU-08)**

- **닉네임 중복 409 의 두 번째 호출자다.** C 가 유니크 위반 → 409 변환을 만들었는데,
  경로가 하나뿐일 때는 *그 변환이 한 곳인지*가 검증되지 않는다. F 가 붙으면 드러난다.
  I-01 의 이중 방어가 DB 유니크라 **여기서도 사전 조회로 끝내지 않는다.**
- **출생연도를 「거부」가 아니라 「받지 않는다」로 한다.** API 설계 2-2 가
  *"`PATCH /users/me/profile` 은 출생연도를 받지 않는다"* 다. 요청 DTO 에 필드를 두고 400 을
  내면 **그 필드가 언젠가 열릴 것처럼 보인다.** 필드를 두지 않으면 계약에 없다.
- **가입 완료 전에는 이 경로를 쓰지 않는다.** 등급이 `SIGNUP` 이라 D 티켓의 판정이 막는다.
  가입 미완료 유저의 수정 경로는 `PUT /users/me/signup-info`(C) 하나다.
- **`profileImageUrl` 을 쓰기로 열지 않는다.** 열면 클라이언트가 임의 URL 을 박을 수 있고,
  그 순간 D-2(서버가 기본 이미지 URL 을 만들지 않는다)가 의미를 잃는다. 업로드는 I 다.

**읽는 쪽 (AU-09)**

- **노출 항목은 넷이다** — 닉네임 · 프로필 이미지 · 한줄소개 · 최근 접속일. 응답에는 `id` 가
  함께 실린다 (화면 계약 3장). 출생연도는 AU-09 의 노출 항목에 없고, `kakaoUserId` 는
  어느 응답에도 나가지 않는다.
- **모집글을 넣지 않는다.** API 설계가 *"건수가 늘면 프로필 조회가 같이 무거워진다"* 로
  갈라 놨다. `/users/{userId}/posts` 는 G 다.
- **`lastSeen` 을 만들지 않는다.** C 가 만든 것을 부른다 (3장).

**이 티켓에서 정한 것 넷** (PR 에 근거를 적었다)

| | 정한 것 | 근거 |
| --- | --- | --- |
| 부분 수정 | 필드가 없거나 `null` 이면 **안 건드린다.** `bio` 의 빈 문자열은 **비움**, `nickname` 의 빈 문자열은 **400** | API 컨벤션의 *"null 을 생략하지 않는다"* 는 **응답 규칙**이고 요청은 정해 두지 않았다. `@Size(min = 1)` 이 「null 은 허용, 빈 값은 거부」를 정확히 표현한다 — `@NotBlank` 는 둘 다 거부해서 부분 수정이 깨진다 |
| 탈퇴·미완료 회원의 공개 프로필 | **404** | API 컨벤션이 *"소프트 삭제된 리소스는 404로 취급한다"* 로 못박았다. 가입 미완료도 함께 404 다 — 닉네임이 `null` 이라 노출 항목 넷 중 하나가 비고, 쓰기가 전부 막혀 있어 남이 그 프로필에 도달할 경로가 없다. 판정을 `isSignupCompleted` 하나로 묶어 **H 가 그대로 따르게** 했다 |
| 신고 버튼의 근거 | **응답에 넣지 않는다.** 화면이 `id` 를 로그인 사용자와 비교한다 | 이 경로는 `PUBLIC` 이라 **요청자에 따라 응답이 갈리면 프론트가 캐시할 수 없다.** 클라이언트는 자기 `id` 를 `GET /users/me` 로 이미 안다 |
| 서비스 자리 | **`ProfileService` 를 두지 않고 `UserService` 에 더했다** | 따로 두면 **유니크 위반 → 409 변환이 두 곳**이 된다. 실제 차단이 DB 제약이라 변환 자리가 갈라지면 한쪽만 고쳐졌을 때 다른 경로가 조용히 500 을 낸다. 이 티켓의 값이 *"그 변환이 한 곳인지 드러난다"* 인데 둘로 만들면 그것을 스스로 깨뜨린다 |

**등급 표와 에러 코드는 건드리지 않았다.** A(STAR-41)가 `SecurityConfig` 의
`MY_PAGE = /api/v1/users/me/**`(모든 메서드 `SIGNUP`) 와 `PUBLIC_READ` 의 `/api/v1/users/*`,
그리고 `EndpointGradeTest.MATRIX` 의 두 줄을 이미 세워 뒀다. `USER_NICKNAME_DUPLICATED` 의
주석도 *"가입(AU-06)과 프로필 수정(AU-08) 양쪽이 쓴다"* 로 이 티켓을 가리키고 있었다.
**확정이 아니라 확인이었다** — D 티켓의 AU-07 과 같은 상황이다.

#### `GET /users/me/comments` 는 Comment 담당이 만든다 — **정해졌다**

**STAR-59 `feat: CM-16 내 댓글 내역` 이 끊겼고 슬기님이 쥐었다.** 아래는 그 판단이 어떻게
갈렸는지의 기록이다 — 되짚을 일이 생기면 근거가 남아 있어야 한다.

| | Identity 가 만든다 | **Comment 가 만든다** |
| --- | --- | --- |
| 판정기·조립기 | 레이어를 넘어가야 한다 | **`companion` 안에서 끝난다** |

| 경로 | API 설계 2-2 회원 섹션에 있다 | 컨트롤러 패키지는 URL 과 무관하다 |

**「판정 코드를 하나로」 라는 원래 근거가 반대를 가리켰다.** 인증·인가 계획이 *"Identity 가 둘 다
만드는 쪽을 제안한다"* 고 적었을 때는 판정기가 없었는데, STAR-56 이
`CommentVisibilityPolicy` 와 `CommentItemAssembler` 를 전부 `companion` 안에 만들었다.
그러면 Identity 가 만드는 쪽이 오히려 레이어를 넘는다.

**G 에는 `/users/me/posts` 만 남는다.** 모집글 탭이고, 이 합의와 무관하게 내 것이다.

**판정기를 새로 만들지 않는다.** STAR-56 이 `companion.domain.CommentVisibilityPolicy` 와
`CommentItemAssembler` 를 만들었고, 여기가 그 두 번째 호출자다. **그런데 자리가 문제다.**

```
identity.presentation.MyCommentController   ← 여기서
        │  부르고 싶은 것
        ▼
companion.presentation.CommentItemAssembler ← 남의 도메인 · 같은 레이어
```

- `CommentVisibilityPolicy` 는 `companion.domain` 이라 어느 쪽이든 부를 수 있다.
- **조립기는 `companion.presentation` 이다.** 게이트 규칙이
  `whereLayer("presentation").mayNotBeAccessedByAnyLayer()` 인데 레이어가 도메인별이 아니라
  `..presentation..` **전체 하나**라, 같은 레이어 안의 참조까지 막는지는 **실측해야 한다.**
  STAR-56 PR 본문은 막힌다고 적었다.
- **G 의 첫 커밋이 이 실측이다.** 막히면 조립기를 옮기거나 공유 지점을 새로 정한다.
  STAR-56 PR 본문이 *"STAR-59 가 `identity.presentation` 에 놓이면 그때 자리를 옮겨야 한다"*
  고 이미 예고해 뒀다.

**인덱스 — 2026-09-08 에 다시 실측했고 앞의 기록이 두 군데 틀렸다.**

**`companion_post` 인덱스는 G 가 직접 낸다.** 앞서 「내 것이 아니라 요청한다」고 적었는데

그래서 Companion 대역이어야 하는 것이고, 그것은 「담당자가 다르다」가 아니라 「표가 그 대역에

그 표를 읽는 쿼리를 G 가 만들므로 **인덱스도 같은 PR 에 든다.** 갈라 놓으면 인덱스를 내는

`V23` 이 비어 있고 **열려 있는 PR 중 Companion 대역 번호를 쥔 것이 없다** — 확인했다.

- **명세서에서 유일한 '선택' 이다.** API 설계도 *"1차에서 뺄 수 있다"* 로 적었다.

### I — `feat: AU-08 프로필 이미지 업로드`

| | |
| --- | --- |
| 담는 것 | **Presigned URL 발급 + 확정** 두 경로 · 저장소 포트와 S3 구현 · 형식·용량 정책 |
| 검증 | 업로드 후 `profileImageUrl` 이 채워지고 **공개 프로필에 반영** · 용량·MIME 위반 400 |
| 선행 | F ✅ · **S3 버킷과 EC2 역할 권한 — 사람 손** |
| DB | **없다.** `profile_image_url` 은 V10 에 있다 |

#### 방향을 바꿨다 — 멀티파트가 아니라 Presigned URL 이다

**이 계획서는 `multipart/form-data` 를 전제로 쓰여 있었다.** API 설계 2-2 도 그렇게 적혀 있다.
배포 환경이 AWS 로 확정되면서 **S3 Presigned URL** 로 간다.

```
멀티파트 (계획서의 전제)
  브라우저 ──파일──▶ 우리 서버 ──파일──▶ S3
                     ▲ 파일이 우리 서버를 통과한다

Presigned URL (실제로 할 것)
  브라우저 ──① 발급 요청──▶ 우리 서버        (파일 없이 메타데이터만)
  브라우저 ◀── 서명된 주소 ──                 (우리 자격증명으로 서명)
  브라우저 ──② 파일──────────────────▶ S3   ← 우리 서버를 지나지 않는다
  브라우저 ──③ 확정 요청──▶ 우리 서버        (그 키를 프로필에 박는다)
```

| | 멀티파트 | **Presigned** |
| --- | --- | --- |
| 파일이 지나는 곳 | 우리 서버 (힙 · 디스크 · 대역폭) | **브라우저 → S3 직결** |
| 서버 설정 | 멀티파트 · 임시 디렉터리 · 최대 크기 | 없다 |
| 자격증명 | 서버가 S3 에 쓴다 | 서버가 **서명만** 한다 |
| 왕복 | 1번 | **3번** |
| 실패 지점 | 한 곳 | **셋** — 그래서 정할 것이 늘어난다 |

**왕복이 늘어나는 대가로 파일이 우리 서버를 통과하지 않는다.** EC2 한 대에 애플리케이션이 올라가
있는 구성이라 그 차이가 크다 — 5MB 이미지 열 장이 동시에 올라오면 멀티파트에서는 그 50MB 가 힙과
대역폭을 함께 먹는다.

#### 계약이 바뀐다 — 엔드포인트가 둘이다

| Method | Path | 권한 | 무엇 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/users/me/profile-image` | `SIGNUP` | **발급.** 형식·용량을 검사하고 서명된 주소를 준다 |
| `PUT` | `/api/v1/users/me/profile-image` | `SIGNUP` | **확정.** 올라간 것을 확인하고 프로필에 박는다 |

**`PUT` 이 계약에 없던 것이다.** API 설계 2-2 에는 `POST` 한 줄뿐이고 `multipart/form-data` 로
적혀 있다 — **위키를 고쳐야 한다** (6장). `EndpointGradeTest.MATRIX` 에도 `POST` 만 있어 한 줄을
더한다. `SecurityConfig` 는 `MY_PAGE = /users/me/**` 가 모든 메서드를 받아 손댈 것이 없다.

#### 확정 단계를 왜 두는가 — 미리 박으면 아바타가 깨진다

발급 시점에 서버는 이미 최종 주소를 안다(키를 서버가 정한다). 그때 바로 `profile_image_url` 에
박아 버리면 왕복이 둘로 줄어든다. **그런데 사용자가 업로드를 취소하면 그 주소가 없는 객체를
가리킨다.**

```
미리 박으면
  발급 → profile_image_url = ".../profile/7/abc.webp"
  사용자가 취소 → S3 에 그 객체가 없다
  → 아바타가 깨진 이미지로 뜬다. 사용자가 되돌릴 방법이 없다
```

**결정 D-2 가 세운 불변식이 깨진다** — *"업로드하지 않은 유저는 `null` 이고 기본 아바타는 프론트
정적 리소스다"*. 없는 객체를 가리키는 주소는 `null` 도 아니고 유효한 값도 아니다.

그래서 확정 단계에서 **S3 에 실제로 있는지 확인한 뒤에만** 박는다.

#### 형식·용량 검증이 세 겹이다 — 서버가 파일을 못 보기 때문이다

**Presigned 는 파일이 서버를 지나지 않아 바이트를 검사할 수 없다.** 검증 기준이 「용량·MIME
위반 400」이므로 그 400 을 낼 자리를 만들어야 한다.

| 겹 | 언제 | 무엇을 본다 | 위반하면 |
| --- | --- | --- | --- |
| ① | **발급** | 클라이언트가 **선언한** 형식과 크기 | **400** — 검증 기준의 그 400 |
| ② | 업로드 | 서명에 형식을 묶어 둔다 | S3 가 서명 불일치로 거절 |
| ③ | **확정** | S3 에 물어본 **실제** 형식과 크기 | **400** — 박지 않는다 |

**①만 두면 클라이언트가 거짓말할 수 있다.** 5MB 라고 선언하고 50MB 를 올리면 ①은 통과한다.
**③이 실제 값을 보는 층**이고 ②는 그 사이를 좁힌다.

#### 정할 것들

- **객체 키에 회원번호를 넣는다** — `profile/{userId}/{uuid}.{확장자}`. 확정 요청이 키를 들고
  오는데 서버가 **접두어로 그 키가 요청자의 것인지 검사한다.** 발급과 확정 사이에 상태를 저장할
  필요가 없어진다 — 키 자체가 소유자를 말한다.
- **UUID 를 넣는다.** 회원번호만으로 키를 만들면 같은 주소를 덮어써서 브라우저·CDN 캐시가 옛
  이미지를 계속 보여준다.
- **남의 키를 들고 오면 「올린 것이 없다」로 답한다.** 「그 키는 남의 것이다」로 답하면 남의 객체가
  존재한다는 사실을 알려준다.
- **버킷 이름이 없으면 `prod` 는 기동하지 않는다.** `JWT_SECRET` · `KAKAO_CLIENT_ID` 와 같은
  판단이다 — 더미로 뜨면 업로드만 조용히 망가진 「정상 기동」이 된다.
- **저장소는 포트와 구현으로 가른다.** 다만 프로파일로 갈지 않고 **버킷 이름이 설정돼 있으면 S3
  구현, 없으면 대역**이 뜬다. 프로파일로 묶으면 자격증명을 가진 개발자가 로컬에서 실물을 확인할
  방법이 없어진다.
- **포트는 `domain` 에 둔다 — 게이트가 잡아서 옮겼다.** 처음 `identity.service` 에 두었더니
  구현이 `infra` 에 있어 **`infra → service` 참조**가 생겼고 `LAYER_DEPENDENCY` 가 일곱 건을
  잡았다. C 의 `SanctionReader` 는 service 에 있지만 **구현도 service 에 있어서** 같은 문제가
  없었다 — 자리를 그것과 맞추면 안 되고 `TokenProvider`(domain) ← `JwtProvider`(infra) 가 이
  모양의 선례다.
- **저장된 주소의 앞부분을 설정으로 뺀다.** 나중에 CloudFront 를 앞에 세우면 도메인만 바뀌는데,
  박아 두면 이미 저장된 값 전부가 마이그레이션 대상이 된다.

#### 안 하는 것

- **삭제 엔드포인트를 두지 않는다.** API 설계 2-2 에 없다. 되돌리려면 `null` 로 만들 방법이
  필요한데 계약에 없어 확인 항목으로 남긴다.
- **옛 객체를 지우지 않는다.** 아바타를 바꾸면 이전 객체가 남는다. S3 수명 주기 규칙으로는 지울 수
  없다 — **현재 아바타와 고아를 구별할 수 없어서** 만료를 걸면 쓰고 있는 것도 지워진다. 코드로
  해야 하는 일이라 별도 관심사로 남긴다 (6장).
- **이미지 리사이즈·최적화를 하지 않는다.** 요구사항에 없고, 하려면 파일이 서버를 지나야 해서
  Presigned 를 고른 이유가 사라진다.

## 5. 확정된 계약

### 응답에 나가지 않는 것

| 값 | 왜 |
| --- | --- |
| `kakaoUserId` | 어느 응답에도. 수집한 개인정보가 회원번호와 직접 입력값뿐이다 (D-2) |
| `birthYear` | 공개 프로필에 없다 (AU-09). `/users/me` 도 마찬가지다 |
| `lastSeenAt` 원본 | **저장 전용**이다. 구간 값 `lastSeen` 으로만 나간다 (도메인 7.2 · V10 주석) |
| `tokensInvalidatedAt` · `withdrawnAt` | 내부 판정용 |

### 커서는 API 컨벤션 공통 규칙을 그대로 쓴다

`items` · `nextCursor` · `hasNext` 세 필드이고, 커서는 **정렬 키 조합을 Base64 로 인코딩한
불투명 문자열**이다. 디코딩 실패는 `INVALID_INPUT` 400 이다.

**catalog 에 선례가 있다** — `EventSlice(items, nextCursor, hasNext)` · `EventCursor`.
G 에서 같은 모양으로 만든다. **공통 타입으로 뽑지 않는다** — 정렬 키가 도메인마다 다르고,
지금 뽑으면 제네릭 하나에 세 도메인의 커서가 매달린다. 셋째 사례가 나올 때 본다.

### `{userId}/posts` 와 `me/posts` 를 합치지 않는다

API 설계가 못박았다. 남의 프로필에서는 **공개된 모집글만**, 내 내역에서는 **내가 쓴 전부**가
보인다. 경로를 합치면 그 분기가 한 핸들러 안으로 들어온다. **같은 조회 메서드를 쓰되
엔드포인트는 둘이다.**

맞다. 이 계획에 남는 일은 부르는 것뿐이다.

### 마이그레이션 번호

Identity/Auth 대역은 **V10~V19** 다. `V10`·`V11`(STAR-40) · `V12`·`V13`(B, 머지됨) · `V14`(C) 가 쥐었고
**이 계획의 네 장은 마이그레이션이 없다.** 컬럼이 V10 에 전부 서 있기 때문이다.

**필요한 인덱스가 전부 남의 대역에 있다** (G). 대역은 사람이 아니라 영역에 붙으므로
내 V14 로 내지 않는다. 번호를 고를 일이 생기면 **표보다 디렉터리를 먼저 본다.**

**I 도 마이그레이션이 없다.** `profile_image_url VARCHAR(500)` 이 V10 에 서 있고, Presigned 는
DB 에 새 컬럼을 요구하지 않는다 — 발급과 확정 사이의 상태를 **객체 키 자체가** 들고 있기 때문이다
(4장 I).

## 7. 함정

- **닉네임 유니크가 세 곳에 걸린다** — 가입(C) · 수정(F) · 탈퇴 익명화(H). 앞의 둘은 409 로
  변환하는 같은 코드를 쓰고, **탈퇴는 위반을 만들면 안 된다.** 셋을 같은 눈으로 보지 않으면
  탈퇴가 조용히 500 이 난다.
- **`PATCH` 는 부분 수정이라 「보내지 않음」과 「null 로 비움」이 다르다.** `bio` 를 지우려는
  요청과 안 건드리는 요청을 DTO 가 구별해야 한다. API 컨벤션이 *"null 은 생략하지 않고
  명시한다"* 인 것은 **응답 규칙**이고 요청은 다르다. F 에서 정하고 PR 에 적는다.
- ✅ **`/users/me` 가 `{userId}` 에 먹히지 않는다 — 실측했다.** 스프링이 리터럴 경로를 변수
  경로보다 먼저 골라 `GET /users/me` 와 `/users/nickname-availability` 가 그대로 간다. 우선순위가
  뒤집히면 남의 정보가 열리는 것이 아니라 **`"me"` 를 `Long` 으로 바꾸다 터진다.** 조용히
  뒤집히지 않게 컨트롤러 테스트 둘로 못박았다.
- **`GET /users/{userId}` 는 `PUBLIC` 이다.** 비회원이 부른다. 인증·인가 계획 5장의
  「여는 쪽 와일드카드에 `**` 를 쓰지 않는다」가 그대로 걸린다 — `/users/*` 로 좁혀야
  `/users/me/...` 가 같이 열리지 않는다. **실측된 사고 유형이다.**
- **`/users/me` 계열이 `{userId}` 패턴에 먹힌다.** `GET /users/me` 와 `GET /users/{userId}`
  가 같은 모양이라 매핑 순서에 따라 `me` 가 `userId` 로 파싱된다. 등급도 다르다
  (`AUTH` vs `PUBLIC`). **F 가 둘을 한 티켓에서 만드니 이 충돌이 그 안에서 드러난다.**
  `EndpointGradeTest.MATRIX` 에 둘 다 적는다.
- **새 엔드포인트를 만들면 두 곳에 적는다** — `SecurityConfig` 와 `EndpointGradeTest.MATRIX`.
  이 계획이 여는 엔드포인트가 여섯이다. 인증·인가 계획 5장이 정한 규칙이고, ②를 빼먹으면
  그 경로의 등급이 검증되지 않는다.
- **`V11__seed_user` 의 더미 7건이 조회 테스트에 섞인다.** F·G 가 목록·단건을 검증하는데
  Flyway 로 들어간 더미가 Testcontainers 에도 존재한다. `deleteAllInBatch` 로 비우면
  뒤 테스트의 전제가 사라진다 — **자기가 만든 행만 정리한다.** C 가 겪는 것과 같은 함정이다.
- **`lastSeen` 구간 경계는 `Clock` 을 주입받아 고정한다.** 「24시간 이내」·「3일 이내」가
  실행 시각으로 갈리면 경계 테스트가 어제와 오늘 다르게 돈다. `ClockConfig` 의 빈이
  KST 이고 도메인 7.2 도 *"구간 계산 기준은 KST"* 다.
- **`profile_image_url` 이 VARCHAR(500) 이다.** S3 주소가 `https://{버킷}.s3.{리전}.amazonaws.com/profile/{회원번호}/{uuid}.webp` 라 100자 안쪽이지만, CloudFront 도메인이 앞에 붙거나 키 규칙이 길어지면 경계가 가까워진다. **주소 앞부분을 설정으로 뺀 이유가 이것이기도 하다** — 길이가 코드에 박히지 않는다.
- **탈퇴 유저의 댓글은 목록에서 사라지지 않는다.** `Comment.status` 를 건드리지 않기
  때문이다. CM-11 의 「하위 대댓글이 있으면 목록에 남는다」와 **다른 축**이라 둘을
  섞으면 안 된다.

### AU-12 를 티켓으로 세지 않은 이유

노출 경로(`GET /users/me` 의 `sanction`)는 C 가 만드는 우리 엔드포인트가 맞다. 그런데
**Identity 쪽에 남는 일이 「no-op 포트를 실구현으로 바꾸는 것」 하나뿐이다.** C 가
`kind: NONE` 고정으로 내면서 포트를 미리 뚫어 두면, 그 뒤는 `Sanction` 을 만드는 쪽이
같은 PR 에서 꽂는 편이 자연스럽다 — D 티켓이 I-14 를 처리한 것과 같은 모양이다.

**C 가 포트를 뚫는 것이 이 결정의 전제다.** 안 뚫으면 Safety 담당이 우리 컨트롤러를
고쳐야 한다. C 의 완료 조건에 그 한 줄이 들어간다.

Identity 담당 전체는 **티켓 아홉 장**이다 — 인증·인가 다섯(A~E)과 이 문서의 넷(F~I).
