# 채팅 메시지·이미지 구현 계획 (chat · Redis)

2차 MVP 의 `CH-07` ~ `CH-18` 중 **메시지·실시간·이미지** 를 **티켓 여덟 장**으로 끊은 실행
계획이다. 지라 상위 항목 **「Redis · 채팅 메시지 · 이미지 업로드」** 가 이 문서의 범위다.

**이 문서의 자리** — 위키는 *무엇을 왜 만드는가*, 이 문서는 *어떤 순서로 만드는가*다.
요구사항 원문·불변식·에러 코드는 여기 옮겨 적지 않는다. 여기에는 **위키만 봐서는 알 수 없는
것** — 티켓 경계, 순서의 근거, 남과 물린 지점 — 만 둔다.

## 2. 순서의 근거

### ① B 가 커서를 정하지 않는다 — C 가 정한다

`V700` 주석이 이 티켓 앞으로 메모를 남겨 두었다.

> 「멤버별 마지막 읽은 지점」 컬럼이 아직 없다. 타입이 `CH-09` 의 커서 정의에 달려 있고
> 그것이 아직 없다. `CH-13`(안 읽은 수) 티켓이 더한다.

**커서의 모양 하나가 셋을 묶는다.**

| 티켓 | 커서를 무엇에 쓰나 |
| --- | --- |
| C (CH-09) | 목록을 거슬러 올라가는 기준. **여기서 정했다 — `messageId` 하나** |
| E (CH-11) | 클라이언트가 「마지막으로 받은 지점」으로 보내는 값 = SSE 의 `id:` 줄 |
| H (CH-13) | 멤버 행에 저장하는 「마지막으로 읽은 지점」 = `BIGINT` 한 칸 |

**C 가 커서를 한 값으로 둔 덕에 E·H 가 싸졌다.** 다른 목록들처럼 `(createdAt, id)` 두 값이었으면
H 의 컬럼이 둘이 되고 E 는 두 값을 합친 무언가를 주고받아야 했다 — `id` 자체가 삽입 순서의
전순서라 덧댈 것이 없다는 것이 근거다 (`MessageCursor` 자바독).

그래서 C 가 E·H 의 선행이다. 순서를 바꾸면 E 나 H 가 커서를 먼저 지어내게 되고,
C 가 다른 모양으로 정하는 순간 둘을 다시 고쳐야 한다.

### ② A 가 맨 앞인 이유는 D 하나다

Redis 가 필요한 것은 **D 의 팬아웃뿐**이다. B·C·F·G·H 는 Redis 없이 돈다.

그런데도 A 를 먼저 하는 이유는 **A 가 인프라를 건드리기 때문**이다. 로컬 compose·EC2
컨테이너·`application-prod.yml`·CD 가 다 걸리고, 이건 코드 리뷰가 아니라 **서버에서
확인해야 끝나는 종류**다. D 를 짜면서 같이 하면 「SSE 가 안 되는 것」과 「Redis 가 안 붙는
것」이 섞여서 원인을 못 좁힌다.

### ③ E 는 선택이 아니다 — 배포가 대화를 끊는다

[인프라 현황](../wiki/05-기록-회고/인프라-아키텍처-현황.md) ③ 이 적은 문제가 SSE 에도
그대로 온다.

```
blue-green 전환   리스너를 green 으로 옮긴다
                    → blue 에 붙어 있던 SSE 연결은 안 끊긴다
그 다음 배포      배포 대상 = blue → docker stop duckmoim-app
                    → blue 의 SSE 가 전부 끊긴다 💥
```

끊기는 것 자체는 막을 수 없다. **끊긴 뒤에 무엇이 일어나는가**가 E 다 —
클라이언트가 다시 붙고, 그 사이 온 N 건을 받는다. E 가 없으면 **배포할 때마다 대화가
말없이 사라진다.** 검증 기준이 「유실 0건」인 이유가 이것이다.

### ④ F 가 B 뒤인 이유

`CH-14` 의 검증 기준이 *「업로드 확인 전 메시지 전송 시 400」* 이다. **메시지 전송 경로가
있어야 판정할 수 있다.** 이미지는 메시지에 붙는 것이지 그 자체가 전송 단위가 아니다.

### ⑤ G 를 F 에서 떼어낸 이유

`CH-16` 이 **비동기 워커**다. 업로드 응답을 기다리게 하지 않는다. 워커는 알림
워커(`NotificationDispatchBatch`)와 같은 모양이 되고, 그쪽의 재시도·중복 방지 논의가
STAR-120 에서 돌고 있다. F 에 섞으면 업로드 실패와 EXIF 실패가 한 PR 에서 뭉친다.

## 3. A — Redis 를 어디에 어떻게 띄우나 (STAR-110)

이 티켓의 본체는 코드가 아니라 **인프라 결정 세 개**다.

### 3.1 어디서 도는가

| 선택지 | 비용 | 문제 |
| --- | --- | --- |
| **ElastiCache** | 가장 싼 노드도 **월 $12 이상** | 지금 관측성까지 전부 $0 로 맞춰 왔다 |
| **EC2 한 대에 도커 Redis** | $0 | 그 한 대가 죽으면 팬아웃이 멈춘다 |
| 앱 컨테이너 안에 | $0 | 인스턴스마다 따로 떠서 **팬아웃이 아예 안 된다** |

**추천은 둘째다.** 근거는 Pub/Sub 이 **상태를 저장하지 않는다**는 점이다. 메시지의 정본은
MySQL 이고 Redis 는 「지금 붙어 있는 사람에게 밀어주는 통로」일 뿐이다. 통로가 끊기면
사용자는 새로고침하면 보이고, 재연결하면 E 가 메운다. **잃는 것이 영구적이지 않다.**

**배포가 Redis 를 죽이지 않는다는 것은 확인했다.**

```bash
docker stop duckmoim-app    # ci-cd.yml 264행 — 이름을 지정해서 멈춘다
```

`duckmoim-redis` 라는 다른 이름의 컨테이너는 배포와 무관하게 계속 돈다.

**메모리는 들어간다.** `t3.medium` 4GB 에 JVM 이 `MaxRAMPercentage=70` 으로 2.8GB,
Alloy 가 ~100MB, 남는 것이 ~1.1GB 다. Pub/Sub 전용 Redis 는 수십 MB 다.
`--maxmemory` 를 걸어 상한을 못박는다.

### 3.2 Redis 가 죽으면 무엇이 멈추어야 하나

**이 티켓이 정하는 가장 중요한 규칙이다.**

```
멈춰도 되는 것    SSE 팬아웃 — 다른 인스턴스에 붙은 사람에게 밀어주기
절대 안 되는 것   메시지 전송 · 목록 조회 · 방 조회
```

Redis 장애가 `POST /messages` 의 500 이 되면, **부가 기능의 장애가 본 기능을 죽이는**
구조가 된다. `NT-01` 이 아웃박스로 막은 것과 같은 실수다 — 그쪽 검증 기준이
*「알림 채널을 죽인 상태에서 댓글 작성 성공률 100%」* 였다. 여기도 같은 성격의 기준을 둔다.

> **통과해야 하는 기준** — Redis 를 내린 상태에서 메시지 전송과 목록 조회가 200 이다.

### 3.3 어느 레이어에 두는가

[아키텍처 컨벤션](../wiki/04-협업-규칙/아키텍처-컨벤션.md) 의 `service` 금지 목록에
**「Redis, Kafka, HTTP Client 직접 사용」** 이 있다. `RedisTemplate` 이 service 에
들어가면 ArchUnit 이 아니라 **리뷰가 잡아야 하는 위반**이 된다.

```
chat/service         MessageFanout 인터페이스에만 의존한다
chat/infra           RedisMessageFanout 이 RedisTemplate 을 쓴다
```

인터페이스를 두면 **테스트가 Redis 없이 돈다**는 이득이 함께 온다. Testcontainers 에
Redis 를 더하는 것은 D 의 팬아웃 테스트 한 곳으로 좁힐 수 있다.

### 3.4 6379 를 어떻게 여는가

**`8080 ← 0.0.0.0/0` 과 같은 방식으로 열면 안 된다.** 6379 는 인터넷에 노출되는 즉시
스캐너에 잡히는 대표 포트이고, 기본 설정에 인증이 없어 열리는 즉시 읽고 쓸 수 있다.
Loki 에 이미 스캐너 흔적이 남아 있었다.

```
새 보안 그룹  duckmoim-redis-sg
   6379  ←  duckmoim-sg (소스를 CIDR 이 아니라 보안 그룹으로)   ✅
   6379  ←  0.0.0.0/0                                        ❌
```

**`requirepass` 를 함께 건다.** 보안 그룹이 맞게 걸렸다는 전제가 깨져도 한 겹 남는다.

두 EC2 가 같은 VPC · 같은 AZ(`2c`)라 사설 IP 로 붙고 **데이터 전송 비용이 없다.**
`172.31.35.164` · `172.31.38.192` 중 Redis 를 띄운 쪽의 사설 IP 가 `REDIS_HOST` 다.

**이건 콘솔에서 사람이 하는 일이다.** 코드로 못 한다.

### 3.5 A 의 커밋 경계

```
1  compose 에 redis · 의존성 · 연결 설정            ← Redis 가 붙는다
2  Redis 를 헬스체크 기여자에서 뺀다                 ← 3.2 의 규칙을 인프라에 새긴다
3  ChatFanout 포트와 Redis 구현                     ← 예외를 삼키는 계약
4  Redis 없이도 도는 것 · 팬아웃이 건너가는 것을 테스트로
5  운영 EC2 에 컨테이너 · 보안 그룹 · REDIS_HOST     ← 사람 손 (3.4)
```

**2 번이 이 티켓의 본체다.** Actuator 는 Redis 를 자동으로 헬스 기여자에 넣는다. 그대로 두면
**Redis 가 죽는 순간 `/actuator/health` 가 DOWN → 두 인스턴스 동시 unhealthy → 전면 503**
이다. `diskspace` 를 끈 것과 똑같은 이유이고, 그때 적은 근거가 그대로 적용된다.

## 4. B ~ H 가 통과해야 하는 기준

명세서 2-1 에서 그대로 가져온 것이다. 창작이 아니라 수집이다.

| | ID | 검증 기준 |
| --- | --- | --- |
| B | CH-07 | 같은 클라이언트 식별자로 두 번 보내면 **한 건**. 비멤버 전송 시 403 |
| B | CH-08 | 방장이 모집을 완료해도 전송 200. **만남시각 + 7일** 경과 후 전송 시 409 |
| C | CH-09 | 페이지 경계에서 누락·중복 없음. **OFFSET 미사용** |
| C | CH-12 | 삭제 후 본문 미노출, **자리표시자 유지** |
| D | CH-10 | **다른 인스턴스에 붙은 멤버의 메시지도 도착한다** |
| E | CH-11 | 끊고 그 사이 N건을 보낸 뒤 재연결 → **유실 0건** |
| F | CH-14 | 허용 밖 형식·크기 400. **업로드 확인 전 메시지 전송 시 400** |
| F | CH-17 | 확정되지 않은 객체가 주기 뒤 사라진다 |
| G | CH-16 | 좌표가 든 사진 업로드 후 **저장된 파일에 EXIF 없음** |
| H | CH-13 | 방 목록의 안 읽은 수가 실제와 일치. **갱신이 방 행을 잠그지 않는다** |
| H | CH-18 | 퇴장 후 메시지 조회 403 |

**두 줄이 성능이 아니라 설계 제약이다.**

- `CH-09` 의 **OFFSET 미사용** — 뒤에서 새 메시지가 계속 들어오므로 OFFSET 은 경계에서
  반드시 어긋난다. 커서여야 하는 이유가 성능이 아니다
- `CH-13` 의 **방 행을 잠그지 않는다** — 도메인 3.1 이 읽은 지점을 멤버 행에 둔 이유다.
  방 행에 두면 여럿이 동시에 읽을 때 서로 기다린다

## 6. 이 여덟 장 밖에 남는 `CH`

명세서 2-1 에 있는데 이 상위 항목에 없는 것들이다. **주인이 정해져야 한다.**

| ID | 요구사항 | 우선 | 비고 |
| --- | --- | --- | --- |
| CH-04 | 퇴장 | 필수 | ✅ **STAR-102 머지됨.** D 가 그 경로에 「연결 끊기」를 얹었다 |
| CH-05 | 방 목록 조회 | 필수 | ✅ **STAR-100 머지됨.** H 의 안 읽은 수가 여기 붙는다 |
| CH-06 | 방 상세 조회 | 필수 | ✅ **STAR-100 머지됨** |
| **CH-15** | **이미지 접근 제어** | **필수** | **5장 #2.** 이게 없으면 F 가 공개 주소를 쓰게 된다 |
| CH-19 | 보관과 파기 (마감 후 90일) | 필수 | 처리방침에 **시행일 2026-09-18** 로 이미 나갔다 |
| CH-20 | 쓰기 자격 (제재 중 차단) | 필수 | ✅ **STAR-103 머지됨** |
| CH-21 | 채팅 신고 | 필수 | `SF-07` 개정과 함께. Safety. **아직 주인 없음** |
| CH-22 | 안내 배너 | 필수 | ✅ **STAR-103 머지됨** |

**주인이 셋 정해졌다** (2026-09-12). `CH-05` · `CH-06` 은 STAR-100 이 머지했고, `CH-20` ·
`CH-22` 는 STAR-103(#126)이 가져갔다.

**`ChatRoom.isWritable` · `isMember` · `CHAT_ROOM_ACCESS_DENIED` 를 STAR-100 이 만들었고
B 와 C 가 그대로 쓴다.** 같은 판정을 두 벌 두지 않으려는 것이고, C 의 목록·삭제도 그 메서드로
「퇴장 후 조회 403」(CH-18)을 함께 막는다 — **`CH-18` 자체는 H 몫이지만 조회 경로를 여는 것이
C 라** 판정을 빼면 구멍이 열린 채로 나간다.

**이제 주인이 없는 것은 `CH-15` · `CH-19` · `CH-21` 셋이다.**

**D 가 `CH-18` 의 스트림 쪽 절반을 함께 막았다** (2026-09-12). 조회는 매 요청 멤버를 보지만
스트림은 붙는 순간 한 번만 보므로, 퇴장(STAR-102)이 그 사람의 연결을 직접 끊는다. 「미는
시점마다 멤버를 다시 본다」와 견주어 **퇴장은 드물고 전송은 잦다**는 이유로 드문 쪽에 비용을
두었다.

**`CH-15` 와 `CH-19` 둘이 급하다.** `CH-15` 는 F 가 그것 없이 나가면 이미지가 공개
주소로 저장되고, 뒤에 고치려면 이미 저장된 주소 전부가 마이그레이션 대상이 된다.
`CH-19` 는 **처리방침에 이미 적혀서 2026-09-18 에 시행**된다 — 문서가 약속한 파기가
코드에 없는 상태로 시행일이 지나는 것은 기능 누락이 아니라 다른 종류의 문제다.
