# 채팅 메시지·이미지 구현 계획 (chat · Redis)

2차 MVP 의 `CH-07` ~ `CH-18` 중 **메시지·실시간·이미지** 를 **티켓 여덟 장**으로 끊은 실행
계획이다. 지라 상위 항목 **「Redis · 채팅 메시지 · 이미지 업로드」** 가 이 문서의 범위다.

**이 문서의 자리** — 위키는 *무엇을 왜 만드는가*, 이 문서는 *어떤 순서로 만드는가*다.
요구사항 원문·불변식·에러 코드는 여기 옮겨 적지 않는다. 여기에는 **위키만 봐서는 알 수 없는
것** — 티켓 경계, 순서의 근거, 남과 물린 지점 — 만 둔다.

## 2. 순서의 근거

### ① B 가 커서를 정하지 않는다 — C 가 정한다

`V700` 주석이 이 티켓 앞으로 메모를 남겨 두었다.

> 「멤버별 마지막 읽은 지점」 컬럼이 아직 없다. 타입이 `CH-09` 의 커서 정의에 달려 있고
> 그것이 아직 없다. `CH-13`(안 읽은 수) 티켓이 더한다.

**커서의 모양 하나가 셋을 묶는다.**

| 티켓 | 커서를 무엇에 쓰나 |
| --- | --- |
| C (CH-09) | 목록을 거슬러 올라가는 기준. **여기서 정했다 — `messageId` 하나** |
| E (CH-11) | 클라이언트가 「마지막으로 받은 지점」으로 보내는 값 = SSE 의 `id:` 줄 |
| H (CH-13) | 멤버 행에 저장하는 「마지막으로 읽은 지점」 = `BIGINT` 한 칸 |

**C 가 커서를 한 값으로 둔 덕에 E·H 가 싸졌다.** 다른 목록들처럼 `(createdAt, id)` 두 값이었으면
H 의 컬럼이 둘이 되고 E 는 두 값을 합친 무언가를 주고받아야 했다 — `id` 자체가 삽입 순서의
전순서라 덧댈 것이 없다는 것이 근거다 (`MessageCursor` 자바독).

그래서 C 가 E·H 의 선행이다. 순서를 바꾸면 E 나 H 가 커서를 먼저 지어내게 되고,
C 가 다른 모양으로 정하는 순간 둘을 다시 고쳐야 한다.

### ② A 가 맨 앞인 이유는 D 하나다

Redis 가 필요한 것은 **D 의 팬아웃뿐**이다. B·C·F·G·H 는 Redis 없이 돈다.

그런데도 A 를 먼저 하는 이유는 **A 가 인프라를 건드리기 때문**이다. 로컬 compose·EC2
컨테이너·`application-prod.yml`·CD 가 다 걸리고, 이건 코드 리뷰가 아니라 **서버에서
확인해야 끝나는 종류**다. D 를 짜면서 같이 하면 「SSE 가 안 되는 것」과 「Redis 가 안 붙는
것」이 섞여서 원인을 못 좁힌다.

### ③ E 는 선택이 아니다 — 배포가 대화를 끊는다

[인프라 현황](../wiki/05-기록-회고/인프라-아키텍처-현황.md) ③ 이 적은 문제가 SSE 에도
그대로 온다.

```
blue-green 전환   리스너를 green 으로 옮긴다
                    → blue 에 붙어 있던 SSE 연결은 안 끊긴다
그 다음 배포      배포 대상 = blue → docker stop duckmoim-app
                    → blue 의 SSE 가 전부 끊긴다 💥
```

끊기는 것 자체는 막을 수 없다. **끊긴 뒤에 무엇이 일어나는가**가 E 다 —
클라이언트가 다시 붙고, 그 사이 온 N 건을 받는다. E 가 없으면 **배포할 때마다 대화가
말없이 사라진다.** 검증 기준이 「유실 0건」인 이유가 이것이다.

### ④ F 가 B 뒤인 이유

`CH-14` 의 검증 기준이 *「업로드 확인 전 메시지 전송 시 400」* 이다. **메시지 전송 경로가
있어야 판정할 수 있다.** 이미지는 메시지에 붙는 것이지 그 자체가 전송 단위가 아니다.

### ⑤ G 를 F 에서 떼어낸 이유

`CH-16` 이 **비동기 워커**다. 업로드 응답을 기다리게 하지 않는다. 워커는 알림
워커(`NotificationDispatchBatch`)와 같은 모양이 되고, 그쪽의 재시도·중복 방지 논의가
STAR-120 에서 돌고 있다. F 에 섞으면 업로드 실패와 EXIF 실패가 한 PR 에서 뭉친다.

## 3. A — Redis 를 어디에 어떻게 띄우나 (STAR-110)

이 티켓의 본체는 코드가 아니라 **인프라 결정 세 개**다.

### 3.1 어디서 도는가

| 선택지 | 비용 | 문제 |
| --- | --- | --- |
| **ElastiCache** | 가장 싼 노드도 **월 $12 이상** | 지금 관측성까지 전부 $0 로 맞춰 왔다 |
| **EC2 한 대에 도커 Redis** | $0 | 그 한 대가 죽으면 팬아웃이 멈춘다 |
| 앱 컨테이너 안에 | $0 | 인스턴스마다 따로 떠서 **팬아웃이 아예 안 된다** |

**추천은 둘째다.** 근거는 Pub/Sub 이 **상태를 저장하지 않는다**는 점이다. 메시지의 정본은
MySQL 이고 Redis 는 「지금 붙어 있는 사람에게 밀어주는 통로」일 뿐이다. 통로가 끊기면
사용자는 새로고침하면 보이고, 재연결하면 E 가 메운다. **잃는 것이 영구적이지 않다.**

**배포가 Redis 를 죽이지 않는다는 것은 확인했다.**

```bash
docker stop duckmoim-app    # ci-cd.yml 264행 — 이름을 지정해서 멈춘다
```

`duckmoim-redis` 라는 다른 이름의 컨테이너는 배포와 무관하게 계속 돈다.

**메모리는 들어간다.** `t3.medium` 4GB 에 JVM 이 `MaxRAMPercentage=70` 으로 2.8GB,
Alloy 가 ~100MB, 남는 것이 ~1.1GB 다. Pub/Sub 전용 Redis 는 수십 MB 다.
`--maxmemory` 를 걸어 상한을 못박는다.

### 3.2 Redis 가 죽으면 무엇이 멈추어야 하나

**이 티켓이 정하는 가장 중요한 규칙이다.**

```
멈춰도 되는 것    SSE 팬아웃 — 다른 인스턴스에 붙은 사람에게 밀어주기
절대 안 되는 것   메시지 전송 · 목록 조회 · 방 조회
```

Redis 장애가 `POST /messages` 의 500 이 되면, **부가 기능의 장애가 본 기능을 죽이는**
구조가 된다. `NT-01` 이 아웃박스로 막은 것과 같은 실수다 — 그쪽 검증 기준이
*「알림 채널을 죽인 상태에서 댓글 작성 성공률 100%」* 였다. 여기도 같은 성격의 기준을 둔다.

> **통과해야 하는 기준** — Redis 를 내린 상태에서 메시지 전송과 목록 조회가 200 이다.

### 3.3 어느 레이어에 두는가

[아키텍처 컨벤션](../wiki/04-협업-규칙/아키텍처-컨벤션.md) 의 `service` 금지 목록에
**「Redis, Kafka, HTTP Client 직접 사용」** 이 있다. `RedisTemplate` 이 service 에
들어가면 ArchUnit 이 아니라 **리뷰가 잡아야 하는 위반**이 된다.

```
chat/service         MessageFanout 인터페이스에만 의존한다
chat/infra           RedisMessageFanout 이 RedisTemplate 을 쓴다
```

인터페이스를 두면 **테스트가 Redis 없이 돈다**는 이득이 함께 온다. Testcontainers 에
Redis 를 더하는 것은 D 의 팬아웃 테스트 한 곳으로 좁힐 수 있다.

### 3.4 6379 를 어떻게 여는가

**`8080 ← 0.0.0.0/0` 과 같은 방식으로 열면 안 된다.** 6379 는 인터넷에 노출되는 즉시
스캐너에 잡히는 대표 포트이고, 기본 설정에 인증이 없어 열리는 즉시 읽고 쓸 수 있다.
Loki 에 이미 스캐너 흔적이 남아 있었다.

```
새 보안 그룹  duckmoim-redis-sg
   6379  ←  duckmoim-sg (소스를 CIDR 이 아니라 보안 그룹으로)   ✅
   6379  ←  0.0.0.0/0                                        ❌
```

**`requirepass` 를 함께 건다.** 보안 그룹이 맞게 걸렸다는 전제가 깨져도 한 겹 남는다.

두 EC2 가 같은 VPC · 같은 AZ(`2c`)라 사설 IP 로 붙고 **데이터 전송 비용이 없다.**
`172.31.35.164` · `172.31.38.192` 중 Redis 를 띄운 쪽의 사설 IP 가 `REDIS_HOST` 다.

**이건 콘솔에서 사람이 하는 일이다.** 코드로 못 한다.

### 3.5 A 의 커밋 경계

```
1  compose 에 redis · 의존성 · 연결 설정            ← Redis 가 붙는다
2  Redis 를 헬스체크 기여자에서 뺀다                 ← 3.2 의 규칙을 인프라에 새긴다
3  ChatFanout 포트와 Redis 구현                     ← 예외를 삼키는 계약
4  Redis 없이도 도는 것 · 팬아웃이 건너가는 것을 테스트로
5  운영 EC2 에 컨테이너 · 보안 그룹 · REDIS_HOST     ← 사람 손 (3.4)
```

**2 번이 이 티켓의 본체다.** Actuator 는 Redis 를 자동으로 헬스 기여자에 넣는다. 그대로 두면
**Redis 가 죽는 순간 `/actuator/health` 가 DOWN → 두 인스턴스 동시 unhealthy → 전면 503**
이다. `diskspace` 를 끈 것과 똑같은 이유이고, 그때 적은 근거가 그대로 적용된다.

## 4. B ~ H 가 통과해야 하는 기준

명세서 2-1 에서 그대로 가져온 것이다. 창작이 아니라 수집이다.

| | ID | 검증 기준 |
| --- | --- | --- |
| B | CH-07 | 같은 클라이언트 식별자로 두 번 보내면 **한 건**. 비멤버 전송 시 403 |
| B | CH-08 | 방장이 모집을 완료해도 전송 200. **만남시각 + 7일** 경과 후 전송 시 409 |
| C | CH-09 | 페이지 경계에서 누락·중복 없음. **OFFSET 미사용** |
| C | CH-12 | 삭제 후 본문 미노출, **자리표시자 유지** |
| D | CH-10 | **다른 인스턴스에 붙은 멤버의 메시지도 도착한다** |
| E | CH-11 | 끊고 그 사이 N건을 보낸 뒤 재연결 → **유실 0건** |
| F | CH-14 | 허용 밖 형식·크기 400. **업로드 확인 전 메시지 전송 시 400** |
| F | CH-17 | 확정되지 않은 객체가 주기 뒤 사라진다 |
| G | CH-16 | 좌표가 든 사진 업로드 후 **저장된 파일에 EXIF 없음** |
| H | CH-13 | 방 목록의 안 읽은 수가 실제와 일치. **갱신이 방 행을 잠그지 않는다** |
| H | CH-18 | 퇴장 후 메시지 조회 403 |

**두 줄이 성능이 아니라 설계 제약이다.**

- `CH-09` 의 **OFFSET 미사용** — 뒤에서 새 메시지가 계속 들어오므로 OFFSET 은 경계에서
  반드시 어긋난다. 커서여야 하는 이유가 성능이 아니다
- `CH-13` 의 **방 행을 잠그지 않는다** — 도메인 3.1 이 읽은 지점을 멤버 행에 둔 이유다.
  방 행에 두면 여럿이 동시에 읽을 때 서로 기다린다

## 7. E — 끊긴 뒤를 어떻게 잇나 (STAR-114)

**이 티켓의 본체도 코드가 아니라 결정 셋이다.** 순서 · 되돌아갈 거리 · 상한.

### 7.1 구독 먼저, 재전송 나중

`open()` 안에서 둘의 순서가 검증 기준을 가른다.

```
❌ 읽고 나서 구독      DB 읽기 ──────▶ 구독 시작
                            ▲
                       이 사이에 발행된 것이 사라진다

✅ 구독하고 나서 읽기   구독 시작 ──────▶ DB 읽기
                            ▲
                       이 사이 것이 중복으로 온다
```

**유실은 못 되돌리고 중복은 되돌린다.** 클라이언트가 이미 `clientMessageId` 로 멱등 처리를
하므로 `messageId` 중복 제거가 새 규칙이 아니다.

그 대가로 **재전송과 실시간이 순서를 섞을 뻔했다.** 처음에는 「클라이언트가 `messageId` 로
정렬하면 된다」로 적었는데 **그것이 틀렸다** (PR #142 리뷰).

```
말풍선 순서    클라이언트가 정렬하면 풀린다              ✅
책갈피 순서    브라우저가 정한다. 클라이언트 몫이 아니다   ❌
```

SSE 명세상 `EventSource` 는 **마지막으로 받은** 사건의 `id` 를 기억한다 — 가장 큰 값이 아니다.
재전송 도중에 실시간 사건이 끼어들면 책갈피가 그 값으로 덮이고, 하필 그때 끊기면 사이 구간이
영영 안 온다.

```
resumeFrom = 101,  재전송 대상 = 102 … 201

선로   102, 103, [실시간 202], 104, 105 …
                    ▲ 구독 스레드가 먼저 썼다
여기서 끊기면  Last-Event-ID = 202
   다음 재연결 → from = 202 − 되돌아갈 거리
   → 104 … 사이 구간이 영영 안 온다      ⚠️ 유실 0건 실패
```

**그래서 재전송이 끝날 때까지 실시간을 연결마다 담아 둔다.** 재전송이 끝나면 잠금 안에서
상태를 바꾸고 큐를 비운다 — 비우는 동안 도착한 것은 잠금에 걸려 큐 뒤에 실린다. **나가는
`id` 가 단조 증가한다.**

### 7.2 `lastId` 가 아니라 조금 앞에서부터 읽는다

`MessageCursor` 자바독이 이 티켓 앞으로 남긴 경고다 (PR #131 리뷰).

```
tx A  INSERT → id 100 ─────────────┐ (커밋 전. 아무도 못 본다)
tx B  INSERT → id 101 → COMMIT     │  클라이언트가 본 마지막 = 101
tx A  ──────────────────── COMMIT     100 이 생긴다
      id > 101 로 이어 읽기           → 100 은 영영 안 온다
```

**`id` 는 삽입 순서이지 커밋 순서가 아니다.** 뒤로 거슬러 읽는 CH-09 은 커서 아래가 이미 전부
커밋돼 있어 영향이 없고, **앞으로 이어 읽는 CH-11 만 깨진다.** 하필 그 검증 기준이 「유실
0건」이다.

`createdAt` 을 커서에 더해도 `BaseEntity` 가 INSERT 시점에 박으므로 똑같이 깨진다. 그래서
**`lastId - 되돌아갈 거리` 부터 읽고 클라이언트가 중복을 거른다.**

**정확한 해법은 아니다.** 되돌아갈 거리는 「동시에 열려 있는 INSERT 개수」의 상한을 가정한
값이고, 그것을 넘는 순간 다시 한 건이 샌다.

**그 개수의 단위를 처음에 「같은 방」으로 적었는데 틀렸다** (PR #142 리뷰). `chat_message.id`
는 표 하나에서 발급되는 수열이라, 창을 만드는 것은 **서비스 전체에서 동시에 열려 있는
INSERT** 다. 그대로 뒀으면 재검토 신호가 영영 안 켜졌을 것이다 — 「한 방에 트래픽이 몰리는
날」을 기다리는데 실제 유실은 방과 무관하게 일어난다.

**그래서 값을 추측하지 않고 커넥션 풀에서 끌어온다.** 동시에 열려 있는 INSERT 수는 DB 커넥션
수를 넘을 수 없다.

```
HikariCP maximum-pool-size  기본 10   (운영에 별도 설정이 없다)
인스턴스                      2대      (blue-green)
                            ─────────
동시 INSERT 상한              20   ←  계산되는 수. 추측이 아니다
되돌아갈 거리                  50   ←  여유를 둔 두 배 반
```

**다시 볼 시점은 「인스턴스가 5대를 넘거나 `maximum-pool-size` 를 25 이상으로 올릴 때」다.**
그때는 이 값을 더 올리는 대신 **커밋 시점에 매기는 별도 순번**(시퀀스 표 · 아웃박스)으로 간다.

**되돌아갈 거리가 재전송 한도를 잡아먹지 않게 했다.** 읽기 상한을 둘의 합으로 두고, 넘침
판정은 **재연결 지점 뒤의 건수**로만 한다 — 한 상한으로 두 가지를 재면 상한이 적힌 값대로
동작하지 않는다.

### 7.3 상한을 넘으면 재전송하지 않고 알린다

며칠 끊겼던 클라이언트 하나가 수만 건을 끌어가면, **그 한 명의 재연결이 인스턴스의 메모리와
선로를 먹는다.**

```
빠진 구간 ≤ 상한     그대로 재전송한다
빠진 구간 > 상한     gap 이벤트만 보낸다 → 클라이언트가 CH-09 목록 API 로 따라잡는다
```

**목록 API 가 이미 커서 페이징이라 새로 만들 것이 없다.** `gap` 에는 `id:` 줄을 싣지 않는다 —
실으면 클라이언트의 재개 지점이 앞으로 밀려 구멍이 굳는다.

### 7.4 남과 물린 자리

| 무엇 | 어디에서 왔나 |
| --- | --- |
| `Last-Event-ID` 의 값 | D 가 `id:` 줄에 `messageId` 를 싣는다 |
| 되돌아갈 거리가 필요한 이유 | C 의 `MessageCursor` 자바독 (PR #131 리뷰) |
| 트랜잭션과 Redis 를 겹치지 않기 | D 의 `ChatRoomMembershipReader` (PR #138 리뷰) |
| 탈퇴 익명화 | AU-11. **재전송이 처음 만난다** — 팬아웃은 탈퇴자를 만날 수 없다 |

**마지막 줄이 이 티켓에서 새로 나온 것이다.** 팬아웃은 방금 보낸 사람의 메시지라 탈퇴자가
아닌데, 재전송은 몇 시간 전 것을 읽어 그 사이 탈퇴한 사람을 만날 수 있다. 팬아웃과 목록이
서로 다른 방식으로 보낸 사람을 만들고 있어서 **그대로 두면 실시간으로 뜬 말풍선만 실명이
남는다.** 사건을 만드는 자리를 하나로 합친다.

## 8. F — 이미지를 어디에 어떻게 두나 (STAR-115)

명세가 구조를 이미 정해 두었다 — **「브라우저가 저장소로 직접 올린다. 서버는 서명과 확인만
한다 (`AU-08` 과 같은 구조)」**. 그래서 이 티켓이 정할 것은 셋이다.

### 8.1 미결 #2 를 닫는다 — `ProfileImageStorage` 와 합치지 않는다

명세서 3장이 「구현 시점에 정한다」로 이 티켓 앞에 남긴 자리다. **따로 둔다.**

| 근거 | |
| --- | --- |
| 컨텍스트 경계 | `ProfileImageStorage` 는 `identity.domain` 이다. chat 이 그것에 의존하면 컨텍스트 간 객체 참조가 생긴다 — 도메인 3.2 는 ID 참조만 허용한다 |
| 포트가 갈라진다 | 채팅은 **삭제**(CH-17)와 나중의 **서명된 GET**(CH-15)이 필요하고, 프로필은 **공개 주소**(`publicUrlOf`)가 필요하다. 채팅에 공개 주소는 <b>있으면 안 되는 메서드</b>다 |
| 키 규칙이 다르다 | 프로필은 `profile/{userId}/…` 로 **키가 소유자를 말한다.** 채팅은 방 멤버 판정이 필요해 키로는 부족하고 DB 행이 판정 근거다 |
| 겹치는 것 | S3 SDK 배선뿐이고 **그것은 이미 공유된다** — `S3Config` 의 `S3Client` · `S3Presigner` 를 양쪽이 주입받는다 |

**합치는 쪽의 이득이 「presign 코드 열 줄」이고, 대가가 「컨텍스트 경계 + 있으면 안 되는
메서드」다.** 값이 맞지 않는다.

### 8.2 공개 주소를 만들지 않는다 — `CH-15` 가 뒤에 오기 때문이다

`CH-15` 는 이 여덟 장에 없고 주인도 없다. 그 검증 기준이 **「공개 주소를 쓰지 않는다」**다.

```
❌ F 가 publicUrlOf 로 주소를 저장하면
      저장된 주소 전부가 CH-15 의 마이그레이션 대상이 된다
      그 사이 주소를 추측해 남의 대화 사진을 볼 수 있다

✅ 객체 키만 저장하고 응답에는 imageId 만 내린다
      CH-15 는 「서명 발급 엔드포인트」만 더하면 된다. 되돌릴 것이 없다
```

**대가를 적어 둔다** — `CH-15` 전까지 **올라간 이미지가 화면에 뜨지 않는다.** 업로드·전송·
목록·정리는 다 돌고 보이는 것만 기다린다. 그 편이 「보이는데 남에게도 보이는」 상태보다 낫다.

**AWS 쪽 전제 하나가 여기 걸린다.** 프로필 이미지가 공개 주소를 쓰므로 버킷에 공개 읽기
허용이 있는데, 그 `Resource` 가 `버킷/*` 이면 `chat/` 도 함께 공개된다. **`profile/*` 로
좁혀져 있어야 이 결정이 성립한다** — 콘솔에서 사람이 확인할 일이다.

### 8.3 상태를 셋으로 두고 발급 시점에 행을 만든다

```
PENDING    서명을 발급했다. 올라왔는지 모른다
CONFIRMED  S3 에 있는 것을 확인했다. 실제 형식·크기를 봤다
ATTACHED   메시지에 실렸다
```

**고아가 두 종류라서 그렇다.**

```
① 올리고 확정 안 함      ← 발급 시점에 행이 없으면 배치가 존재 자체를 모른다
② 확정했는데 전송 안 함   ← CONFIRMED
```

프로필(AU-08)은 발급 때 DB 를 안 건드린다. **그쪽은 지울 필요가 없어 고아를 추적할 이유가
없었다** — 덮어써도 되는 한 장이고, 남은 객체가 비용 말고는 해가 없다. 채팅은 `CH-17` 이
「주기 뒤 사라진다」를 요구한다.

`ATTACHED` 가 `chat_message.image_id` 와 겹쳐 보이는데, **그 중복이 배치의 인덱스다** —
안 두면 고아를 찾을 때마다 `chat_message` 에 `NOT EXISTS` 를 건다.

### 8.4 F 의 커밋 경계

```
1  V704 · ChatImage · 정책 · Message 가 이미지를 갖는다
2  ChatImageStorage 포트와 S3 구현 (발급 · 확인 · 삭제)
3  발급·확정 API 와 에러 코드
4  전송이 이미지를 싣는다 — 확정 안 된 것은 400
5  고아 정리 배치 (CH-17)
6  계획서 갱신
```

**4 번이 검증 기준 두 줄을 동시에 지나는 자리다** — 「업로드 확인 전 전송 시 400」과, 멱등
대조에 이미지를 더하는 일(PR #125 리뷰가 만든 `requireSameRequest`)이 같이 온다.

### 8.5 남과 물린 자리

| 무엇 | |
| --- | --- |
| `S3Config` · `S3Client` · `S3Presigner` | AU-08 이 만들어 둔 것을 그대로 쓴다 |
| 배치 모양 | `NotificationExpiryBatch` 와 같다 — `@Scheduled` 를 service 에 두고 잠그지 않는다 (ADR 0009) |
| **PR #142 (E)** | ⚠️ `AuthoredMessage` · `MessageEvent` · `MessageItemResponse` · `ChatMessageQueryRepositoryImpl` · `ChatMessageSendService` 가 양쪽에서 바뀐다. 응답 셋에 `imageId` 를 더해야 해서 피할 수 없다 — #142 머지 뒤 develop 을 한 번 합쳐 해소한다 |
| `CH-16` (G) | 업로드된 바이트를 이 티켓은 건드리지 않는다. EXIF 워커가 `CONFIRMED` 와 `ATTACHED` 사이에 끼어들 자리를 남겨 둔다 |

## 9. G — 좌표를 어떻게 벗기나 (STAR-116)

명세가 **「업로드 뒤 비동기 워커가 벗긴다」**로 구조를 정했다. F 가 바이트를 서버에 안 거치게
만들어서 올리는 순간에는 벗길 기회가 없고, 올라간 뒤 꺼내서 벗기는 수밖에 없다. 이 티켓이
정할 것은 넷이다.

### 9.1 EXIF 를 수명주기에 섞지 않는다 — 전송은 워커를 안 기다린다

```
섞으면     CONFIRMED → EXIF 처리 중 → EXIF 끝 → ATTACHED
                           ▲ 워커 한 주기(최대 10초) 동안 전송이 400
따로 두면   수명주기   PENDING → CONFIRMED → ATTACHED         전송은 이쪽만 본다
           EXIF      PENDING ──────────────────▶ STRIPPED   보여주는 쪽은 이쪽을 본다
                             └─────────────────▶ FAILED
```

`chat_image.exif_status` 를 **따로 둔다** (`V705`). 사용자는 확정 직후에 보내는데 워커는 최대
한 주기 뒤에 돌기 때문이다. **기본값이 `PENDING`** 이라 이미 배포된 F 의 사진도 전부 워커
대상이 된다 — 좌표 든 사진이 운영에 이미 있을 수 있다.

### 9.2 CH-15 와의 계약 — 벗기기 전에는 서명하지 않는다

**전송이 안 기다리는 대신 보여주는 쪽이 기다린다.** CH-15(STAR-104 · 권소희)가
`ChatImage#isExifStripped()` 가 참일 때만 서명 URL 을 발급한다.

| `exif_status` | CH-15 가 할 일 |
| --- | --- |
| `PENDING` | 아직 서명하지 않는다 — 「처리 중」. 최대 한 주기(10초) |
| `STRIPPED` | 서명한다 |
| `FAILED` | **영구히 서명하지 않는다.** 원본에 좌표가 남은 채다 |

**두 티켓이 동시에 진행돼서 이 표가 경계다.** 방 멤버 판정 · 첨부 여부 같은 나머지 조건은
CH-15 의 몫이라 `isExifStripped` 에 섞지 않았다.

### 9.3 ⚠️ 워커는 버전을 올리지 않는다 — 셋이 한 행을 쓴다

F 의 리뷰에서 `ChatImage` 에 `@Version` 이 들어갔다. 그런데 이제 **한 행을 쓰는 주체가 셋**이다.

```
확정 · 전송      status · content_type · byte_size · version
고아 정리 배치    status · version                        (벌크 UPDATE)
EXIF 워커        exif_status · exif_attempts · exif_next_attempt_at   (벌크 UPDATE)
```

**워커는 확정 직후, 사용자가 보내는 바로 그 몇 초 사이에 돈다.** 두 가지 사고가 그 자리에 있다.

```
워커가 버전을 올리면
   전송 findById (v0) → 워커 STRIPPED (v1) → 전송 attach WHERE version=0 → 400
   → 정상 사용자가 맞는다

엔티티가 모든 열을 다시 쓰면 (JPA 기본)
   전송 findById (exif=PENDING) → 워커 STRIPPED → 전송 attach 가 exif=PENDING 까지 되씀
   → 워커의 결과가 지워진다
```

그래서 **워커는 `exif_*` 열만 쓰는 조건부 UPDATE** 로 쓰고, **`ChatImage` 에
`@DynamicUpdate`** 를 붙여 엔티티 갱신이 바뀐 열만 쓰게 했다. 세 주체가 **서로 다른 열을 쓴다**는
것이 이 설계의 전제이고, `ChatImageExifWorkerTest` 가 **두 트랜잭션을 실제로 갈라** 붙들고 있다
(한 영속성 컨텍스트로 흉내 내면 `merge` 가 운영과 다른 경로를 탄다).

### 9.4 재인코딩하지 않는다 — 방향 한 칸만 남기고 나머지는 전부

| 형식 | 버린다 | 남긴다 |
| --- | --- | --- |
| JPEG | APP1(Exif · XMP) · APP13(IPTC) · COM · 그 밖의 APPn · **EOI 뒤 전부** | APP0 · APP2(ICC) · APP14 · 영상 마커 |
| PNG | `eXIf` · 텍스트 청크 · `tIME` · 모르는 보조 청크 · IEND 뒤 | 필수 청크 · 렌더링 보조 청크 |
| WEBP | `EXIF` · `XMP ` · 모르는 청크 (+ VP8X 플래그 · RIFF 크기) | VP8X · ICCP · ANIM · ANMF · ALPH · VP8 · VP8L |

**남길 것을 적고 나머지를 버린다.** 지울 것을 적으면 모르는 제조사 세그먼트에 좌표가 실려 와도
통과한다. **EOI 뒤**를 버리는 것도 같은 이유다 — 제조사 트레일러와 모션 포토의 영상이 거기 붙고,
영상에도 위치가 실린다.

**방향(Orientation) 한 칸은 새로 써서 남긴다.** 전부 지우면 센서 방향 그대로 저장하는 기기의
세로 사진이 옆으로 누워서 뜬다. 원본 블록을 고쳐 쓰지 않고 **값 하나만 꺼내 26바이트 블록을
새로 만든다** — GPS 포인터 하나를 놓쳐도 좌표가 남는 방식을 피한다.

> ⚠️ **검증 기준 해석이 걸린 자리다.** 「EXIF 없음」을 「위치·식별 정보를 담은 EXIF 없음」으로
> 읽었다. 문자 그대로 전부 지워야 하면 방향을 쓰는 한 줄을 빼면 된다 — 리뷰에서 확인받는다.

**형식은 파일 앞 바이트로 판정한다.** `content_type` 은 클라이언트가 붙인 헤더라, 그것을 믿으면
「image/png」로 올린 다른 파일이 형식별 처리를 빗나가 좌표가 그대로 남는다. 셋 다 아니거나
구조가 깨졌으면 **재시도 없이 `FAILED`** 다.

### 9.5 덮어쓰기는 조건부다 — 행 없는 객체를 되살리지 않는다

```
워커   내려받기 (ETag = A) ─── 벗기기 ───────────── PUT
고아 정리                         행 삭제 · 객체 삭제
                                                   ▲ 조건 없이 쓰면 객체가 되살아난다
                                                     (행은 없다 — F 의 CH-17 이 없애려던 쓰레기)
```

`If-Match: A` 로 조건을 걸어 그 사이 사라졌거나 바뀐 객체에는 쓰지 않는다. `awssdk 2.29.52`
에 `PutObjectRequest#ifMatch` 가 있는 것을 바이트코드로 확인했고, **IAM 추가 권한은 없다.**

### 9.6 선점과 재시도는 알림 워커를 그대로 따른다

`FOR UPDATE SKIP LOCKED` + `exif_next_attempt_at` 리스 (ADR 0008). 값만 다르다.

| | 알림 | EXIF | 왜 다른가 |
| --- | --- | --- | --- |
| 주기 | 10초 | 10초 | 벗기기 전에는 안 보이니 이것이 곧 「처리 중」의 길이 |
| 한 번에 집는 수 | 100 | **10** | 한 장이 최대 10MB 내려받기 · 재작성 · 업로드 |
| 리스 | 30초 | **2분** | 한 청크를 다 처리하는 시간보다 넉넉하게 |
| 재시도 · 백오프 | 3회 · 1m/5m/25m | 같다 | — |

**영구 실패와 일시 실패를 가른다.** 형식을 모르거나 구조가 깨진 파일은 몇 번 해도 같아서 바로
`FAILED`, 네트워크 · 권한 실패는 백오프 뒤 재시도한다. 일시 장애 한 번에 `FAILED` 로 굳히면
좌표 든 사진이 **영구히 안 보인다.**

### 9.7 리뷰에서 막은 둘

**① 이미지 작업이 배치 스케줄러를 붙잡으면 SSE 하트비트가 멈춘다.** 배치 스케줄러는 스레드가
**둘**인데 `@Scheduled` 가 **일곱**이고, 그중 하나가 하트비트다.

```
배포 직후   스레드 1  EXIF 워커 — V705 기본값 PENDING 이라 기존 사진 전부를 차례로 (몇 분)
           스레드 2  모집 마감 배치
           하트비트  발화할 스레드가 없다
+60초      keep-alive 가 안 나가 ALB 유휴 타임아웃에 SSE 가 무더기로 끊김
```

지금까지의 배치는 DB 만 짧게 썼다. 이미지 작업은 **한 장마다 S3 로 10MB 를 주고받는다.** 그래서
`@Scheduled` 는 **넘기기만** 하고 본체는 전용 스레드(`ChatImageJobExecutor`, 스레드 둘)에서 돈다
— #145 가 하트비트의 Redis 호출을 뺀 것과 같은 종류다. **F 의 고아 정리 배치도 같은 이유로 함께
옮겼다** (S3 삭제 최대 1만 건). S3 클라이언트에는 시간 상한이 없어 **시도 20초 · 호출 60초**를
걸었다.

**② 서명 PUT 주소를 5분 안에 다시 쓰면 벗긴 사진이 원본으로 되돌아간다.**

```
20:00:03  좌표 든 원본 PUT → 확정 → 전송
20:00:10  워커가 벗기고 덮어씀                  exif = STRIPPED
20:01:30  같은 주소로 원본을 다시 PUT          S3 = 좌표 든 원본 ⚠️  DB 는 STRIPPED
          → CH-15 가 믿고 서명 → 방 멤버에게 좌표가 나간다
```

이 구멍 자체는 F 부터 있었지만 G 가 CH-15 와 맺는 계약이 「`STRIPPED` 면 안전하다」라서 **그
약속이 거짓이 되는 자리**가 됐다. 발급 서명에 **`If-None-Match: *` 를 묶어 주소를 한 번만 쓰게**
했다 — 헤더를 빼면 서명이 틀리고, 넣으면 객체가 이미 있을 때 S3 가 412 로 거절한다. 전송 뒤
같은 크기의 다른 사진으로 **바꿔치기**하는 길도 같이 막힌다.

| 검토한 방법 | 판단 |
| --- | --- |
| **`If-None-Match: *`** ✅ | 서버 한 줄. 클라이언트가 헤더 하나를 더 보내고, 버킷 CORS 허용 헤더에 추가 |
| 벗긴 파일을 새 키로 · `object_key` 교체 | 옛 주소로 다시 올린 객체가 **행 없는 쓰레기**로 남는다 |
| 벗긴 뒤 ETag 를 저장해 CH-15 가 대조 | 보여줄 때마다 HEAD 가 한 번 더, 경계가 남의 티켓으로 넘어간다 |
| 서명 만료 뒤에만 처리 | 사진이 최대 5분 동안 안 보인다 |

> ⚠️ **프론트와 AWS 에 한 줄씩 필요하다.** PUT 에 `If-None-Match: *` 헤더 · 채팅 버킷 CORS 의
> `AllowedHeaders` 에 `If-None-Match`. 둘 중 하나라도 빠지면 **업로드가 서명 불일치나 CORS 로 실패한다.**

### 9.8 G 의 커밋 경계

```
1  V705 · ExifStatus · ChatImage 의 EXIF 칸 · @DynamicUpdate
2  형식별 무손실 메타데이터 제거기 (JPEG · PNG · WEBP) + 검증 기준 테스트
3  저장소 포트에 내려받기 · 조건부 덮어쓰기
4  선점 · 처리 서비스 (버전을 안 올리는 조건부 UPDATE)
5  워커 · 설정 · 테스트에서 이미지 스케줄러 둘 끄기
6  (리뷰) 업로드 주소를 한 번만 쓰게 한다 — If-None-Match
7  (리뷰) 이미지 작업을 전용 스레드로 · S3 시간 상한
8  계획서 갱신
```

**5 번에 F 가 빠뜨린 것이 하나 섞였다.** `ChatImageCleanupBatch` 의 cron 이 `build.gradle` 에서
꺼져 있지 않았다 — 하루 한 번이라 드러나지 않았지만 새벽 4시 20분에 테스트를 돌리면 남의
테스트가 만든 사진을 치운다.

## 10. H — 어디까지 읽었는지를 어디에 두나 (STAR-117)

`CH-13`(안 읽은 수) · `CH-18`(나간 사람 열람 차단) 두 장이다.

### 10.1 읽은 지점은 멤버 행에 둔다 — 방 행이 아니라

검증 기준의 두 줄 중 하나가 **「갱신이 방 행을 잠그지 않는다」**다. 성능 희망사항이
아니라 **설계 제약**이고, 도메인 모델링 「3.1 경계와 트랜잭션 범위」가 근거를 적어 두었다
— *여럿이 동시에 읽어도 서로 기다리지 않아야 한다.*

```
방 행에 두면                          멤버 행에 두면 (이 티켓)
──────────────                        ──────────────────────
chat_room                             chat_room_member
  id                                    room_id  user_id  last_read_message_id
  last_read_by_7                         3        7       120   ← 7 이 고친다
  last_read_by_11                        3       11        98   ← 11 이 고친다
  ...                                    3       12       null
                                      
5명이 대화를 보면                      각자 자기 행만 고친다
같은 행 하나를 5명이 고친다            → 잠금이 겹치지 않는다
→ 줄을 선다
```

`Message` 가 `chat_room` 밖에 있는 것과 같은 판단이다 — **전송이 방 행을 건드리지
않는다**를 CH-07 이 지켰는데, 읽음 표시를 방 행에 두면 그보다 훨씬 잦은 쓰기가
그 자리로 들어온다.

그래서 갱신이 **멤버 행 하나를 고치는 조건부 `UPDATE` 한 문장**이다. 엔티티를 읽어
고치지 않는다 — 읽으면 `ChatRoom` 이 딸려 오고 그 순간 방 행이 트랜잭션에 들어온다.

```sql
UPDATE chat_room_member
   SET last_read_message_id = :id
 WHERE room_id = :roomId AND user_id = :userId AND left_at IS NULL
   AND (last_read_message_id IS NULL OR last_read_message_id < :id)
```

마지막 줄이 **뒤로 가지 않게** 한다. 기기 둘에서 보내면 늦게 도착한 요청이 먼저
도착한 것보다 앞선 지점일 수 있고, 그때 배지가 되살아난다. **예외가 아니라 0행
갱신**이다 — 뒤늦은 요청은 오류가 아니다.

그리고 **그 방에 실제로 있는 번호까지만** 민다.

```sql
   AND :id <= (SELECT MAX(id) FROM chat_message WHERE room_id = :roomId)
```

**앞으로만 미는 규칙과 겹치면 범위 밖 값 한 번이 영구가 되기 때문**이다 (PR 리뷰).

```
클라이언트가 messageId 대신 Date.now() 를 한 번 보내면
──────────────────────────────────────────────────────
  last_read = 1789281753213        방의 최대 번호 = 3
       │
       ├─ 새 메시지 4, 5 가 와도 4 < 1789281753213 → 배지 0
       └─ 3 으로 되돌리려 해도 「뒤로 안 간다」에 막힘 → 복구 불가
```

악의가 아니라 **실수로 걸리는 쪽**이다 — 타임스탬프 · 다른 방의 번호가 모두 같은
결과를 낸다.

**깎지 않고 거부한다.** 방의 최대 번호로 `LEAST` 하는 방법도 있지만 그것은 「방 끝까지
읽었다」를 **서버가 대신 단언하는 것**이라 정말 안 읽은 말이 읽은 것이 된다. 거부하면
배지가 실제보다 높게 남는데 — **그쪽이 안전한 실패다.** 배지가 남는 것은 사용자가 보고
알 수 있고, 0 이 되는 것은 온 메시지를 숨긴다. 알림 억제가 *"억제는 부속이고 알림은 본
기능이라 열리는 쪽으로 실패한다"* 로 정한 것과 같은 방향이다.

### 10.2 커서가 `messageId` 하나인 것은 C 가 정해 둔 덕이다

`V700` 이 이 칸을 비워 두고 갔다. 그때 「읽은 지점」을 시각으로 둘지 번호로 둘지가
열려 있었는데, **C(CH-09)가 목록 커서를 `(id)` 하나로 정하면서** 같이 닫혔다 —
화면이 스크롤로 쥐고 있는 값이 곧 `messageId` 라 그대로 올려 보내면 된다.

시각으로 뒀다면 클라이언트가 자기 시계를 올려 보내게 되고, 그러면 **읽은 지점이
서버의 순서와 갈린다** (AUTO_INCREMENT 가 삽입 순서라는 것을 E 가 이미 겪었다).

### 10.3 안 읽은 수에서 내 메시지를 뺀다

```
방 3 의 메시지                     나(7)의 last_read = 120
  118  from 11                     ┐
  120  from 11   ← 여기까지 읽음    ┘ 안 셈
  121  from 7    ← 내가 보낸 것      안 셈  ★
  122  from 11                     ┐
  123  from 11                     ┘ 2 건     → 배지 2
```

★ 를 빼지 않으면 **말할 때마다 자기 배지가 오른다.** 「전송할 때 읽은 지점을 함께
민다」로도 풀리지만, 그러면 전송이 멤버 행까지 쓰게 되어 10.1 이 지킨 성질이 도로
깨진다 — 빼는 쪽이 쓰기를 하나도 늘리지 않는다.

**지우거나 가린 메시지는 센다.** 말풍선이 자리표시자로 남기 때문이다 (CH-12 · AD-09).
화면에 줄이 보이는데 배지가 안 오르면 검증 기준 「실제와 일치」가 그 자리에서 깨진다.

### 10.4 목록 질의가 `EXISTS` 에서 `JOIN` 으로 바뀐다

안 읽은 수를 세려면 **내 멤버 행의 읽은 지점**이 필요한데 `EXISTS` 는 있는지만 답하고
값을 꺼내 주지 않는다. 멤버 행은 방마다 하나뿐이라 조인해도 행이 늘지 않는다.

**CH-18 이 그 조인 조건 안에 있다** — `left_at IS NULL`. 바꾸기 전의 `EXISTS` 가
하던 일을 그대로 조인이 한다. 「나간 방이 목록에서 사라진다」가 새 코드가 아니라
**원래 있던 한 줄이 자리를 옮긴 것**이다.

### 10.5 CH-18 은 거의 코드가 아니라 테스트다

판정은 `ChatRoomMembershipReader` 한 군데에 이미 있고 (`isMember` 가 `leftAt` 을
본다), 나간 사람은 저절로 막힌다. 문제는 **그 판정을 부르는 입구가 여럿**이고 새 입구를
내면서 한 줄을 빠뜨리면 **그 입구만 열린 채로 초록불**이라는 것이다.

그래서 입구를 한 곳에 열거한다 (`ChatLeftMemberAccessTest`).

| 문 | 닫히는가 |
| --- | --- |
| 방 목록 | 없어진다 (10.4 의 조인) |
| 방 상세 · 대화 · 전송 · 사진 서명 · 읽은 지점 | 403 `CHAT_ROOM_ACCESS_DENIED` |
| 스트림 | 끊긴다 — `ChatStreamServiceTest` 가 본다 (실물 Redis 가 필요해 그쪽에 둔다) |
| **신고 접수** | **열려 있다** ★ |

★ 가 이 목록의 본체다. 닫는 것만 테스트하면 다음 사람이 「나간 사람은 전부
막는다」로 읽고 접수까지 닫는다. 2026-09-12 에 **막으면 「괴롭히고 나가기」 길이
생긴다**는 이유로 접수는 열어 두기로 닫힌 미결이다 (2차 명세서 3장 1번).

### 10.6 위키가 이 티켓에 맡긴 한 줄

> `CH-18` 이 들어오면 화면에서 `messageId` 를 얻을 길이 따로 필요하고, 그것은
> STAR-117 의 몫이다. (2차 명세서 3장 · API 설계 2-6)

**서버가 낼 길이 아니라는 것이 이 티켓의 답이다.** 대화를 다시 열어 주면 CH-18 이
무의미해지고, 「신고용으로만 열린 조회」를 두면 그것이 곧 우회로가 된다.

- 신고 화면은 **대화 화면에서 진입**한다. 나가기 전에 그 번호를 쥐고 넘어간다.
- 나간 **뒤에** 결심한 사람은 `ROOM` 또는 `USER` 를 지목한다 — 둘 다 이미 열려 있는
  대상이고, 관리자가 AD-08 로 대화를 읽어 판단한다.
- 서버 쪽 의무는 **접수가 멤버십을 보지 않는 것** 하나이고 이미 그렇다
  (`ReportTargetReader` 는 대상의 존재만 본다). 10.5 의 ★ 가 그것을 못박는다.
