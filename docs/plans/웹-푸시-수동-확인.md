# 웹 푸시 수동 확인 (NT-15)

`NT-12` ~ `NT-14` 는 자동 검사가 지킨다. **`NT-15` 만 사람이 본다.**

> **검증 기준** — 설치한 PWA 에서 푸시 수신 확인

관련: [STAR-132](https://youstar.atlassian.net/browse/STAR-132) · PR #157 ·
[API 설계 「웹 푸시 (NT-12 ~ NT-15)」](../wiki/02-설계-아키텍처/API-설계.md)

---

## 1. 왜 자동으로 못 하나

앞의 커밋들이 증명하는 것은 **「우리 서버가 올바른 요청을 만든다」**까지다. 그 뒤 구간은 우리 코드가 아니다.

| 구간 | 누가 답하나 |
| --- | --- |
| 실제 배달 | FCM · Mozilla · Apple 의 서버 |
| 홈 화면 설치 상태 | **iOS 는 설치한 PWA 에만 도달한다.** 브라우저 탭에서는 아예 안 온다 |
| 앱이 닫힌 상태에서 깨우기 | 브라우저의 Service Worker 런타임 |

**iOS 하나는 반드시 필요하다.** 거기만 설치를 요구하고, 나머지는 브라우저에서도 와서 iOS 에서 되면 대개 다 된다.

## 2. 준비

### 2-1. 백엔드 — 배포 로그부터 본다

**이것을 먼저 확인하지 않으면 전부 「안 온다」로 나오고 원인을 엉뚱한 데서 찾게 된다.**

```
[WebPushConfig.notificationPushSender] 웹 푸시 켜짐. subject=mailto:...
```

이 줄이 아니라 아래가 뜨면 **시크릿이 컨테이너에 안 들어간 것**이다.

```
[WebPushConfig.notificationPushSender] VAPID 키가 없어 웹 푸시를 끈다. 인앱은 그대로다.
```

그때는 EC2 에서 전달 여부를 센다. **값은 찍지 않는다** — 비밀키가 터미널과 셸 히스토리에 남는다.

```bash
docker inspect duckmoim --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -c VAPID
# 3 이 나와야 한다
```

### 2-2. 프론트 — 공개키가 들어갔는지

Vercel 환경변수 `NEXT_PUBLIC_VAPID_PUBLIC_KEY` 가 **배포된 빌드에** 들어가 있어야 한다. 빌드 타임에 박히므로 값을 넣은 뒤 **재배포**가 필요하다.

### 2-3. 기기

| | 무엇 | 왜 |
| --- | --- | --- |
| 필수 | iPhone (Safari) | 설치 요구 조건이 가장 까다롭다 |
| 필수 | Android 또는 데스크톱 Chrome | 「기기 둘」 기준을 보려면 둘이 필요하다 |
| 계정 | 둘 | 한쪽이 댓글을 달아야 다른 쪽에 알림이 간다 |

### 2-4. 미리 알아 둘 것

**발송이 10초 주기 배치다.** 누르고 **최대 10초** 기다린다. 「즉시 안 온다」를 실패로 세지 않는다.

## 3. 시나리오

### A. 설치한 PWA 에서 수신 — 본 기준

```
1. iPhone Safari 로 접속
2. 공유 → 「홈 화면에 추가」
3. 홈 화면 아이콘으로 앱을 연다        ← 반드시. 사파리 탭에서 열면 안 온다
4. 「알림 켜기」 → 권한 허용
5. 앱을 완전히 종료 (앱 스위처에서 위로 밀어 닫기)
6. 다른 계정으로 그 사람의 모집글에 댓글을 단다
7. 10초 안에 잠금화면에 알림이 뜨는지 본다
8. 알림을 탭 → 그 모집글의 그 댓글로 가는지 본다
```

**8번이 `url` 을 본다.** 엉뚱한 데로 가면 서버가 만든 경로와 프론트 라우트가 어긋난 것이다
(PR #157 「고민한 부분 ①」).

### B. 기기 둘에서 등록하면 둘 다 받는다 (`NT-12`)

같은 계정으로 **폰과 노트북 둘 다** 알림을 켜고, 댓글 하나에 **양쪽 다** 뜨는지 본다.

### C. 알림 종류 셋 (`NT-06` · `NT-07`)

| 무엇을 | 누가 받나 |
| --- | --- |
| 모집글에 댓글 | 글쓴이 |
| 댓글에 답글 | 부모 댓글 작성자 |
| 채팅방에 메시지 | **그 방을 안 보고 있는** 멤버 |

**셋째가 `NT-07` 을 겸한다.**

```
방을 열어 둔 채로 상대가 메시지를 보낸다   →  푸시가 오면 안 된다
방을 닫고 다시 보낸다                      →  와야 한다
```

### D. 종류별 수신 설정 (`NT-11`)

설정에서 **채팅만 끄고** 댓글 알림은 계속 오는지 본다.

끈 종류는 아웃박스에 행 자체가 안 생기므로 **인앱 알림함에도 안 나타나야 한다.** 알림함에 뜨는데 푸시만 안 오면 그것은 다른 고장이다.

### E. 해제와 만료 (`NT-14`)

```
「알림 끄기」를 누른다  →  더 이상 안 온다
```

행이 사라졌는지 확인한다.

```sql
SELECT id, user_id, created_at FROM push_subscription WHERE user_id = ?;
-- endpoint 와 키는 조회하지 않는다. 기기를 특정하는 값이고 암호화 키다
```

**진짜 만료(410)는 인위적으로 만들기 어렵다.** 브라우저 설정에서 사이트 데이터를 지우면 구독이 무효가 되는데, 그 뒤 알림을 보내면 서버가 그 행을 지워야 한다. 로그로 본다.

```
[WebPushNotificationSender.forget] 만료된 구독을 지웠다. subscriptionId=...
```

## 5. 안 될 때 — 어디부터 보나

원인이 프론트인지 백엔드인지 빨리 가르는 순서다.

| 증상 | 먼저 볼 곳 |
| --- | --- |
| 「알림 켜기」가 아무 반응 없음 | **프론트** — 권한 요청 흐름 |
| 켜졌는데 `push_subscription` 에 행이 없음 | **프론트** — `POST` 호출 실패. 네트워크 탭 |
| 행은 있는데 안 옴 | **백엔드** — 기동 로그(2-1)와 워커 로그 |
| 데스크톱은 오는데 iOS 만 안 옴 | **설치 여부.** 홈 화면 아이콘으로 열었는지 |
| 알림은 오는데 문구가 이상함 | **프론트** — Service Worker 의 조립 로직 |
| 알림을 탭했더니 엉뚱한 데로 감 | **백엔드** — `url` 조립 |
| 한 기기에 같은 알림이 여러 번 | **백엔드** — 구독이 쌓였다. 행이 둘인지 본다 |

**「행이 있는가」가 가장 빠른 분기점이다.** 없으면 프론트에서 서버까지 못 온 것이고, 있으면 서버에서 기기까지 못 간 것이다.

## 6. 이 문서가 다루지 않는 것

| 무엇 | 어디 |
| --- | --- |
| 구독 저장 · 해제 규칙 | `PushSubscriptionTest` |
| 만료 · 실패 분류 | `WebPushExpiryTest` |
| VAPID 키 형식 | `WebPushConfigTest` |
| 푸시 실패가 인앱을 롤백시키지 않음 | `NotificationChannelBoundaryTest` |

**위 넷은 자동 검사가 지킨다.** 여기서 다시 보지 않는다.
