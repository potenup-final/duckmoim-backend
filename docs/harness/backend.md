# 백엔드 하네스

팀 하네스 문서의 백엔드 절. `duckmoim-backend` 저장소 기준.

하네스는 "에이전트에게 잘 부탁하는 법"이 아니다. **사람이 매번 다시 설명하지
않아도 되게 만드는 저장소 설정**이다. 부탁은 지켜지지 않을 수 있고, 설정은
지켜진다.

프론트 절이 이 정의를 먼저 세웠다. 백엔드는 같은 정의에서 출발해 **두 군데가
갈라진다.** 아래 배치의 전부가 그 두 군데다.

## 프론트와 무엇이 다른가

### 사람이 3명이고 셋 다 에이전트를 쓴다

프론트 절은 강제 계층(CODEOWNERS·브랜치 보호)을 **일부러 비워뒀다.** 프론트를
한 사람이 맡고 있어 승인으로 막을 상대가 없었기 때문이다.

백엔드는 다르다. 셋이 같은 `main` 위에서 병렬로 움직이고, 셋의 에이전트가 같은
공용 파일에 손이 닿는다. **막을 상대가 실제로 있다.** 그래서 이 문서는 프론트가
비워둔 마지막 줄을 채운다.

### 컨벤션을 빌드에서 검증할 수 있다

위키의 컨벤션 문서 넷은 합계 944줄이고 이례적으로 구체적이다. 그런데 전부
"사람이 읽는 문서"라 **강제력이 0이다.** 지금 상태로는 에이전트가 위반해도 아무
일이 일어나지 않고, 사람이 리뷰에서 같은 지적을 반복한다.

프론트에는 이걸 옮길 곳이 없었다. 백엔드에는 있다. Java 생태계에는 의존성
방향·네이밍·포맷을 빌드에서 검사하는 도구가 성숙해 있고, **위키 규칙의 상당수가
기계가 판정할 수 있는 형태로 적혀 있다.** 이게 백엔드 하네스의 중심이다.

## 루프 한 바퀴

```
Jira 티켓 → 진행 중        브랜치 자동 생성 (feat/STAR-30)
        ↓
[1] 컨텍스트 확보        요구사항 ID(AU-06)의 검증 기준 → 테스트 목록
        ↓
[2] 구현                domain → infra → service → presentation 순서
        ↓
[3] 자체 채점            ./gradlew check
        ↓  ←── 실패하면 [2]로 돌아간다. 사람을 부르지 않는다
[4] PR                  사람 칸만 채운다 (Jira 블록은 자동)
        ↓
[5] CI 초록 + 리뷰 1명 → develop 머지
```

**설계의 전부는 [3]이다.** 에이전트가 사람을 부르지 않고 스스로 반복할 수 있는
구간이 있어야 루프다. 그 구간이 없으면 이건 루프가 아니라 *사람이 매번 같은
지적을 반복하는 왕복*이고, 지금 위키 944줄이 정확히 그 상태다.

[2]의 순서가 `domain → infra → service → presentation` 인 것은 취향이 아니다.
의존성이 그 방향으로만 흐르기 때문에 (아키텍처 컨벤션 "의존성 방향") 역순으로
쓰면 아직 없는 것을 참조하게 되고, 에이전트는 그때 인터페이스를 임의로 만들어
채운다. 그렇게 만들어진 인터페이스가 나중에 지워지지 않는다.

## [1] 컨텍스트 확보 — 무엇을 모으는가

산출물은 **이 티켓이 통과해야 하는 테스트 목록** 하나다. 테스트 컨벤션이
*"요구사항 명세의 검증 기준이 곧 테스트 목록이다. 별도로 테스트 케이스를 설계하지
않는다"* 라고 못박았으므로, [1]은 **창작이 아니라 수집이다.**

| # | 무엇 | 어디에 | 없으면 |
|---|---|---|---|
| 1 | 요구사항의 **검증 기준** | MVP 명세서 2장, 표의 마지막 열 | 테스트가 얕아진다 |
| 2 | **불변식**과 검증 위치 | 도메인 모델링 5장 (`I-01`~`I-15`) | 두 겹으로 막을 것을 한 겹만 막는다 |
| 3 | **유비쿼터스 언어** | 도메인 모델링 1장 (식별자 24개) | 이름이 API 계약으로 굳는다 |
| 4 | **에러 코드와 status** | API 설계 4장 (이미 20개 확정) | 같은 의미의 코드가 중복 생성된다 |
| 5 | **설계 결정** | API 설계 5장 (`D-1`~`D-6`) · ADR | 이미 기각된 대안을 고른다 |
| 6 | **애그리게이트 경계** | 도메인 모델링 3장 | 트랜잭션 범위가 틀린다 |

**5 가 가장 안 찾아보면서 피해가 크다.** D-1 은 *Refresh 를 httpOnly 쿠키에 두지
않는다* 다 — 프론트(Vercel)와 API(AWS)가 다른 도메인이라 서드파티 쿠키가 되고
Safari ITP 에 막히기 때문이다. 그런데 리프레시 토큰 구현을 맡기면 에이전트는 거의
확실히 쿠키를 쓴다. **그게 일반적인 모범 사례고 학습 데이터에 그렇게 적혀 있다.**
D-3(*모집글 삭제를 두지 않는다*)도 같다 — 에이전트는 CRUD 를 완성하려 든다.

그래서 [1]의 성격은 이렇다. **모르는 것을 채우는 단계가 아니라, 에이전트가 기본값으로
알고 있는 것을 덮어쓰는 단계다.** 여기를 건너뛰면 에이전트는 막히지 않는다.
"일반적으로 맞는" 코드를 자신 있게 짜고, 그게 이 프로젝트에서 틀렸다는 사실은
리뷰에 가서야 드러난다.

### ID 한 개만 보면 절반만 안다

요구사항과 불변식이 서로를 인용한다.

```
요구사항  AU-06 닉네임 중복 방지                        ← MVP 명세서
    ↕
불변식    I-01  닉네임은 유일하다                        ← 도메인 모델링 5장
          검증 위치: 사전 조회(AU-06) · 이중 방어: 유니크 제약 → 409
    ↕
에러코드  UserErrorCode.NICKNAME_DUPLICATED  409  근거 I-01   ← API 설계 4장
```

티켓이 `AU-06` 만 줘도 `I-01` 을 같이 봐야 완전해진다. **어디서 강제하는지는
불변식 표에만 적혀 있다.** 그리고 그게 테스트 컨벤션이 "반드시 테스트하는 것"으로
분류한 동시성 항목과 바로 이어진다 — 이중 방어가 DB 제약이면 검증은 통합 테스트다.

어느 접두어가 어느 문서 소속인지는 위키 README 의 **ID 체계** 표에 있다.

### 위키를 서브모듈로 단다

위키는 **별도 저장소이고 PRIVATE 다.** 백엔드에서 작업하는 에이전트는 파일로도 못
읽고, private 이라 웹으로도 못 가져온다. 그대로 두면 [1]은 매번 사람이 붙여넣는
일이 되고, 그건 하네스가 없애려는 것 자체다.

```
docs/wiki/   →  potenup-final/duckmoim-wiki   (서브모듈)
```

확인한 것 셋이다.

- **CI 는 영향받지 않는다.** `actions/checkout` 의 `submodules` 는 기본값이 false 이고
  `ci-cd.yml` 은 그 키를 넘기지 않는다. Dockerfile 도 `gradlew`·`gradle`·`build.gradle`·
  `settings.gradle`·`src` 만 COPY 한다
- **`./gradlew build` 는 그대로 통과한다** (서브모듈 추가 후 확인)
- **핀이 고정된다.** 백엔드는 위키의 특정 커밋을 기록한다. 위키가 갱신되면 백엔드에서
  포인터를 올려야 최신이 된다. 이게 서브모듈의 대가다

대안으로 저장소를 나란히 두고 상대경로로 가리키는 방법이 있었는데 택하지 않았다.
**팀원의 로컬 배치에 의존하고, 배치가 다르면 조용히 실패한다.**

서브모듈 초기화와 `submodule.recurse` 설정은 **Gradle 이 켜준다** — `installGitHooks`
와 같은 자리에 `initWiki` · `configureSubmoduleRecurse` 를 뒀다. 위키가 PRIVATE 이라
접근 권한이 없으면 실패하는데, **그때 조용히 넘기지 않고 경고를 찍는다.** 빌드는
통과하는데 에이전트가 스펙을 못 읽는 상태가 가장 나쁘다 — 알아채지 못한 채로
"일반적으로 맞는" 코드가 나온다. 경고가 실제로 찍히는 것까지 확인했다.

### 서브모듈로도 안 잡히는 것

위의 여섯 가지는 **위키에 무엇이 있는지 세서 만든 목록이다.** 공급을 재고한 것이고
수요를 잰 것이 아니다. 그래서 서브모듈을 달아도 남는 구멍이 있다. 두 종류다.

**문서가 없어서 못 주는 것.**

- **애플리케이션 환경변수 이름.** `application.yml` 에는 앱 이름과 Swagger 설정만 있다.
  카카오 키, JWT 서명키, DB 접속, CORS 오리진이 없다. 에이전트는 이름을 지어내고
  셋이 각자 다른 이름을 짓는다. **배포 쪽 시크릿은 해결됐다** — 위키 03 의
  배포-파이프라인 4장이 GitHub Secrets 를 문서화했고, 03 README 가 남은 범위를
  "애플리케이션 환경변수는 없음"으로 좁혔다
- **로컬 실행 방법.** 위키 04 의 "로컬 개발 환경 셋업"이 ⬜ 다. 프론트 절에는
  「화면 바꾸면 눈으로 확인한다」가 있는데 백엔드에는 대응물이 없다. *테스트가
  통과했다는 것은 뜬다는 뜻이 아니다*
- **CORS 허용 오리진.** CI/CD 계획의 함정 표가 "`allowedOrigins` 에 Vercel 도메인
  추가"라고 적었는데 그 도메인이 어느 문서에도 없다

**문서로 줄 수 없는 것.**

- **프론트의 실물 계약.** EV-02 가 "`EventItem` 14필드를 DB 컬럼에 대응"을 요구하지만
  **`EventItem` 의 정의가 위키에 없다.** 프론트 저장소 `src/types.ts` 에 있고, 표기가
  어긋난다 — 실물은 `starts_on` · `subject_type` (snake_case), API 컨벤션은
  **camelCase 강제**. EV-08 의 검증 기준이 "전환 전후 노출 내용 동일"인데 그 사이에
  표기 변환이 끼어 있다. 위키만 읽은 에이전트는 이 충돌을 볼 수 없다.
  **위키 서브모듈로 해결되지 않는다** — 아래 "남은 것"에 넘겼다
- **지금 누가 무엇을 하고 있는지.** 셋이 병렬이고 역할 분담이 미정이라, 옆 사람이
  만들고 있는 클래스를 또 만든다. 문서가 아니라 *현재 상태*다. 수단은 열린 PR 과 브랜치 목록
- **선례.** 도메인 코드가 0줄이라 선례가 없다. 에이전트는 선례를 아주 강하게 모방하므로
  **첫 도메인이 컨벤션을 어기면 그 위반이 셋에게 복제된다.** 문서로 해결되는 문제가
  아니라 "첫 도메인은 사람이 더 촘촘히 본다"는 운영 규칙이 필요하다
- **실패 이력.** 위키 05 에 기록이 붙기 시작했다 (2026-09-02 강사 피드백). 다만 그건
  회의 기록이고, *코드를 쓸 때 걸리는* 함정은 아직 없다. 프론트는 겪은 함정을
  `CLAUDE.md` 의 코드 관습에 쌓아뒀다. 백엔드도 생기는 대로 거기 쌓는다

**그리고 이 목록도 추측이다.** 정직하게 목록을 만드는 방법은 하나뿐이다 —
**첫 티켓을 한 바퀴 돌리고, 에이전트가 사람에게 물은 것을 그대로 기록하는 것.**
질문한 항목이 곧 컨텍스트 구멍이다. 하네스는 한 번에 설계해서 맞히는 것이 아니라
루프를 돌려 구멍을 관측하는 쪽이다.

### 전부 읽히게 하지는 않는다

서브모듈은 위키를 *읽을 수 있게* 만드는 것이고, *항상 읽는* 것이 아니다. 컨벤션
넷만 944줄이고 위키 전체는 2,500줄이 넘는다. 매 세션에 다 얹으면 컨텍스트를
먹고 준수율이 떨어진다 — `CLAUDE.md` 를 200줄 아래로 두는 것과 같은 이유다.

`.claude/rules/` 의 `paths:` 와 스킬이 **티켓에 걸린 부분만** 가리키게 한다.

## 무엇을 어디에 두는가

| 층 | 수단 | 언제 | 세기 |
|---|---|---|---|
| 참고 | `CLAUDE.md` | 세션 시작마다 전부 | 안 지켜질 수 있다 |
| 참고 | 오토 메모리 (`MEMORY.md`) | 세션 시작마다 앞 200줄 | 안 지켜질 수 있다 |
| 참고 | `.claude/rules/*.md` + `paths:` | 해당 레이어 파일을 열 때 | 안 지켜질 수 있다 |
| 참고 | 스킬 | 호출하거나 관련될 때 | 안 지켜질 수 있다 |
| 1차 방어 | `permissions.deny` | 도구 호출 시점 | **Edit·Read 만** 본다 |
| 2차 방어 | PreToolUse 훅 | 도구 호출 시점 | 도구 전부. 로컬이라 끌 수 있다 |
| 2차 방어 | git 훅 | 커밋 시점 | 로컬이라 끌 수 있다 |
| **강제** | **`./gradlew check`** | **커밋 전 · CI** | **CI 가 막는다** |
| **강제** | **브랜치 보호 · CODEOWNERS** | **푸시 · 머지 시점** | **진짜 막힌다** |

아래 두 줄이 프론트 표에 없던 것이다. 그리고 이 표에서 **에이전트를 안 쓰는
팀원에게도 걸리는 것은 아래 두 줄뿐이다.** 위쪽 넷은 에이전트를 쓰는 사람에게만
값이 있다. 규칙을 진짜로 팀 전체에 걸고 싶으면 아래 두 줄로 내려보내야 한다.

## 게이트 — `./gradlew check`

### 왜 CI 를 안 고쳐도 되는가

Gradle 의 `build` 는 `check` 에 의존하고, Spotless·Checkstyle 은 자기 태스크를
`check` 에 매단다. CI 는 이미 `./gradlew build` 를 돌리고 있다.

실측으로 확인했다. `./gradlew build --rerun-tasks` 의 태스크 목록이다.

```
> Task :spotlessJavaCheck
> Task :checkstyleMain
> Task :checkstyleTest
> Task :test
> Task :check
> Task :build
```

**`ci-cd.yml` 을 한 줄도 고치지 않고 CI 가 잡는다.** 더 중요한 것은 에이전트가
로컬에서 보는 실패와 CI 가 보는 실패가 같아진다는 점이다. 다르면 에이전트는
로컬 초록불을 믿고 PR 을 열고, 사람이 CI 를 대신 읽어준다.

### 검증한 조합

Gradle 9.7.1 + Boot 3.5.16 + Java 17 툴체인에서 실제로 돌려봤다. Gradle 9 는
아직 새 계열이라 플러그인 호환이 실제 위험이었다.

| 도구 | 버전 | 결과 |
|---|---|---|
| Spotless | 7.0.2 | 돈다 |
| Checkstyle | 10.21.1 (Gradle 내장 플러그인) | 돈다. `main` 과 `test` 양쪽 검사 |
| ArchUnit | 1.4.0 (테스트 의존성. Gradle 플러그인 아님) | 돈다 |

전체 `check` 가 **웜 데몬에서 3초.** 게이트가 싸다는 것이 중요하다. 비싸면
에이전트가 [2]↔[3] 을 돌리지 않고 한 번에 다 짜려 하고, 그러면 루프가 아니다.

**지금 도입하는 것이 가장 싸다.** Spotless 를 나중에 켜면 첫 실행이 기존 코드
전체를 리포맷해서 diff 가 폭발한다. 지금 소스는 여덟 파일이다.

### 게이트가 이미 한 번 일했다

작업 중에 STAR-26(Swagger 도입)이 `main` 에 머지됐다. 리베이스로 받아오자
**`OpenApiConfig.java` 와 새 테스트 2개가 곧바로 Spotless 에 걸렸다** — 게이트가
생기기 전에 쓰인 탭 코드였다.

이것이 게이트가 **자기가 안 쓴 코드에서 작동한다는 첫 증거**다. 규칙을 스스로
지키는 것과 남이 지키게 만드는 것은 다른 일이고, 하네스가 노리는 것은 후자다.

같이 관측한 것이 하나 있다. STAR-26 의 테스트는 메서드명(`servesApiDocs`)과
`@DisplayName` 이 다 컨벤션에 맞았다. 다만 `@DisplayName` 이 "API 문서가 열려
있다" 처럼 마침표가 없는데, 테스트 컨벤션은 어투를 `~다.` 로 통일하라고 한다.
기계로 잡을 수 있는 항목이지만 지금 켜면 남의 코드를 고쳐야 해서 켜지 않았다.
**게이트를 늘릴 때는 이미 있는 코드를 고칠 각오가 같이 필요하다.**

### 함정 — 빈 레이어에서 ArchUnit 이 죽는다

도메인 코드가 0줄인 상태에서 레이어 규칙을 켜면 빌드가 깨진다. 실측 메시지다.

```
Architecture Violation [Priority: MEDIUM] - Rule '...' was violated (4 times):
Layer 'domain' is empty
Layer 'infra' is empty
Layer 'presentation' is empty
Layer 'service' is empty
```

`withOptionalLayers(true)` 를 붙이면 통과한다. **그런데 그러면 규칙이 아무것도
검증하지 않으면서 초록불이 된다.** CI/CD 계획 문서가 Phase 1 에서 경고한 것과
같은 상태다 — *사실 아무것도 검사하지 않는 CI를 몇 주간 믿고 쓰는 일.*

### 그래서 규칙이 살아있음을 증명한다

규칙 정의를 한 곳에 두고, **위반 픽스처를 일부러 만들어 규칙이 그것을 잡는지
검사한다.**

```java
// src/test/java/com/duckmoim/architecture/
//   LayerRules.java              규칙의 단일 정의
//   LayerDependencyTest.java     프로덕션 코드를 검사한다 (지금은 빈 레이어라 통과)
//   LayerRuleIsAliveTest.java    규칙이 위반을 잡는지 검사한다
//   fixture/service/ViolatingPaymentService.java   service → infra 직접 참조
//   fixture/infra/PaymentJpaRepository.java

EvaluationResult result = LayerRules.LAYER_DEPENDENCY.evaluate(fixture);

assertThat(result.hasViolation()).isTrue();
assertThat(result.getFailureReport().toString()).contains("ViolatingPaymentService");
```

`@AnalyzeClasses` 는 `ImportOption.DoNotIncludeTests` 를 쓰므로 픽스처가
프로덕션 검사에 섞이지 않는다. 실측으로 둘 다 통과하는 것을 확인했다.

이건 CI/CD 계획 Phase 1 의 완료 조건 ②(*일부러 테스트를 깨뜨린 PR 에서 ❌ 가
뜨는지 확인*)를 **사람 손에서 떼어내 테스트로 만든 것**이다. 규칙을 추가할
때마다 살아있음 테스트를 같이 추가한다. 이게 이 게이트를 믿을 수 있게 만드는
유일한 근거다.

### 무엇을 옮기고 무엇을 남기나

| 위키 규칙 | 옮길 곳 | 지금 |
|---|---|---|
| 의존성 방향 4개 규칙 | ArchUnit | ✅ |
| service 가 기술 객체·infra 구현 직접 참조 금지 | ArchUnit | ✅ |
| domain 이 다른 레이어를 참조하지 않음 | ArchUnit | ✅ |
| 저장소 인터페이스는 domain 에 선언 | ArchUnit | ✅ |
| `@Transactional` 은 service 에만 | ArchUnit | ✅ |
| Entity 의 `@Data`·무분별한 `@Setter` 금지 | ArchUnit | ✅ |
| 테스트 메서드명 `pay_pointIsNotEnough` 형식 | Checkstyle `MethodName` | ✅ |
| `@Test` 에 `@DisplayName` 누락 | ArchUnit (메서드 어노테이션) | ✅ |
| 로그 prefix `[Class.method]` | Checkstyle `RegexpSinglelineJava` | ✅ |
| 로그 문자열 더하기 금지 | Checkstyle `RegexpSinglelineJava` | ✅ |
| 포맷·임포트 순서 | Spotless | ✅ |
| Entity 를 Response 로 직접 반환 금지 | ArchUnit | 첫 엔티티 이후 |
| H2 금지 (테스트 컨벤션) | Gradle 의존성 금지 규칙 | 첫 엔티티 이후 |
| 커밋 제목 `[KEY]` 누락 | CI 정규식 워크플로 | ✅ |

**기계가 못 보는 것은 남는다.** 이건 CLAUDE.md 와 사람 리뷰의 몫이다.

- service 메서드가 비즈니스 흐름으로 **읽히는가**
- 도메인 서비스가 하나의 명확한 역할을 갖는가
- TODO 에 해소 조건이 적혀 있는가
- ErrorCode 가 같은 의미로 중복 생성되지 않았는가

### 요구사항 ID 를 테스트에 박는다

위 목록의 마지막 항목 하나는 반쯤 자동화할 수 있고, 이 저장소에서 값이 가장 크다.

MVP 명세서는 요구사항마다 ID(`AU-06`, `EV-03`…)와 검증 기준을 갖고 있다. 테스트
컨벤션은 이미 **"요구사항 명세의 검증 기준이 곧 테스트 목록"** 이라고 못박고
별도 설계를 금지했다. 두 문서가 이미 ID 로 이어져 있다는 뜻이다.

그러면 테스트에 요구사항 ID 를 어노테이션으로 달고, **명세 ID 대비 테스트가
없는 것을 목록으로 뽑을 수 있다.** 리뷰에서 "이 요구사항의 검증 기준이 테스트로
있는가"를 눈으로 대조하는 대신 게이트가 답한다.

커버리지 수치 목표를 두지 않겠다는 테스트 컨벤션의 결정과도 어긋나지 않는다.
재는 것이 *코드 줄 수*가 아니라 *합의된 요구사항 목록*이다.

## 팀 연동 위에서 지킬 것

Jira, GitHub, Slack 이 물려 있다. 프론트 절과 같은 이유로 **에이전트가 손으로
하면 안 되는 일이 있다.** 손으로 하면 자동화가 만든 것과 어긋난다.

### 브랜치를 만들지 않는다

Jira 티켓을 **진행 중으로 옮기면** 워크플로가 만든다. 제목 접두사 한 단어가
브랜치·라벨·커밋 타입 셋을 다 결정한다. 인정하는 것은 여섯 개뿐이다.
`feat` `fix` `refactor` `test` `chore` `docs`.

**기준 브랜치는 저장소의 default branch 다.** `jira-dispatch.yml` 이
`gh api repos/... --jq .default_branch` 로 가져온다. 아래 "브랜치 전략" 절이
여기에 걸린다.

### 커밋 메시지에 `[KEY]` 를 붙이지 않는다

`.githooks/prepare-commit-msg` 가 브랜치명에서 키를 뽑아 붙인다.
백엔드는 **Gradle 이 켜준다** — `build.gradle` 의 `installGitHooks` 가
`compileJava` 에 매달려 있어 첫 빌드에서 활성화된다. 프론트는 `npm install` 의
`prepare` 스크립트가 같은 일을 한다.

```bash
git config core.hooksPath      # .githooks 가 나와야 한다
```

**그래도 강제가 아니다.** `git -c core.hooksPath=/dev/null commit` 이면 훅을 못
찾는다. 그래서 `[KEY]` 누락은 위 표대로 **CI 검사로 올려야 한다.** 훅은 빠른
피드백, CI 가 강제. 아직 안 만들었고 "남은 것"에 적어뒀다.

### 위키를 `docs/wiki` 안에서 고치지 않는다

서브모듈 디렉터리는 기본적으로 **detached HEAD 다.** 거기서 고쳐 커밋하면 어느
브랜치에도 없는 커밋이 생기고, 다음 `submodule update` 에서 조용히 사라진다.

그래서 `docs/wiki` 는 **읽기 전용이다.** 위키 수정은 항상 별도 클론에서 한다.
그러면 두 작업이 완전히 분리되고 이 함정을 아예 만나지 않는다.

**위키를 고칠 때** — 서브모듈이 있기 전과 똑같다.

```bash
cd ~/projects/duckmoim/duckmoim-wiki      # 별도 클론
git pull && git commit -m "docs: ..." && git push
```

위키에는 `.githooks` 가 없어 커밋 제목에 `[KEY]` 가 붙지 않는다. 정상이다.
`main` 직접 커밋이 관행이다.

**백엔드에서 포인터를 올릴 때** — 위키를 **푸시한 뒤에** 한다.

```bash
git submodule update --remote docs/wiki   # --remote 가 핵심
git add docs/wiki
git commit -m "chore: 위키 서브모듈 포인터 갱신"
```

- **`--remote` 가 없으면 반대로 동작한다.** 맨 `git submodule update` 는 최신을 당기는
  것이 아니라 *기록된 핀으로 되돌린다*
- 커밋에 담기는 것은 **커밋 SHA 한 줄**이다. 위키 내용이 백엔드로 복사되지 않는다
- 안 푸시한 위키 커밋을 가리키면 **팀원의 `submodule update` 가 실패한다**

**평소 백엔드를 커밋할 때** — 대개 신경 쓸 것이 없다. 읽기 전용이라 변하지 않는다.
함정은 `git add -A` 와 `git commit -a` 다. 서브모듈이 어떤 이유로든 다른 커밋에
놓여 있으면 **포인터가 조용히 같이 올라간다.** `git status` 에
`modified: docs/wiki (new commits)` 가 뜨는지 본다.

덤으로, 백엔드의 **각 커밋이 위키 커밋 하나를 못 박는다.** 옛 커밋을 체크아웃하면
그때의 위키가 따라온다 — "이 코드가 어느 스펙을 보고 쓰였는지"가 보존된다.

### PR 본문 앞부분을 쓰지 않는다

`pr_body.py` 가 `<!-- jira:start -->` 마커 사이에 Jira 정보를 붙인다. 요구사항과
배경은 Jira 에 있으니 옮겨 적지 않는다.

**여기서 드리프트가 이미 일어났다.** 프론트 절은 공용 파일 넷이 "지금은 넷 다
내용이 같다"고 기록했지만, STAR-20 의 `chore: 이슈·PR 템플릿 적용` 이 백엔드
`PULL_REQUEST_TEMPLATE.md` 를 일반형으로 교체했다. 이제 두 저장소가 다르다.

게다가 새 템플릿의 `🔗 관련 이슈` · `📌 개요` · `✨ 변경 사항` · `🔥 변경 이유`
칸은 **자동으로 붙는 Jira 블록과 내용이 겹친다.** 사람이 채우면 같은 내용이 PR
하나에 두 번 적히고, 안 채우면 빈 칸이 남는다. 프론트 쪽 템플릿(리뷰 포인트 ·
테스트 방법 · 스크린샷 · 체크리스트)은 자동화가 채우지 않는 것만 묻는 형태였다.

**어느 쪽으로 통일할지는 합의 사항이다.** 다만 지금처럼 갈라진 채로 두면
프론트 절이 "걱정할 것은 한쪽만 바뀌어 두 저장소가 다르게 동작하는 것"이라고
적어둔 상황 그 자체다.

## 브랜치 전략 — `develop` 을 만들고 설정을 고친다

문서와 현실이 갈라져 있다. 확인한 사실 셋이다.

1. **`develop` 브랜치가 원격에 없다.** `main` 과 작업 브랜치뿐이다. 협업 규칙
   문서에만 존재한다
2. **Jira 자동화는 default branch 기준으로 브랜치를 딴다.** `develop` 을 만들어도
   default 를 바꾸지 않으면 계속 `main` 에서 갈라진다
3. **CI 는 `main` 으로 향하는 PR 에서만 돈다** (`pull_request: branches: [main]`).
   `feature/STAR-30 → develop` PR 은 **빌드도 테스트도 안 돌고 초록불 없이 머지
   가능하다**

세 곳을 고친다.

- [ ] `develop` 브랜치 생성 (`main` 에서)
- [ ] default branch 를 `develop` 으로 변경 — 이래야 Jira 가 딴 브랜치의 base 와
      PR 의 기본 base 가 맞는다
- [ ] `ci-cd.yml` 의 `pull_request.branches` 에 `develop` 추가.
      **`deploy` 잡은 건드리지 않는다** — `github.ref == 'refs/heads/main'` 조건이
      하드코딩돼 있어 develop 머지로 배포가 나가지 않는다

이걸 안 고치면 루프의 [5]("CI 초록")가 성립하지 않고, 마지막 관문을 CI 가 아니라
사람이 떠맡는다.

## 손대면 안 되는 곳

| 경로 | 상태 | 이유 |
|---|---|---|
| `.githooks/**` | 금지 | 팀 공용. 프론트 저장소에 사본이 있다 |
| `.github/scripts/**` | 금지 | 팀 공용 Jira 연동 |
| `.github/workflows/jira-*.yml` | 금지 | 팀 공용 |
| `.github/PULL_REQUEST_TEMPLATE.md` | 금지 | 팀 공용 |
| `.github/workflows/ci-cd.yml` | 물어봄 | 잘못 고치면 프로덕션에 배포가 나간다 |
| `gradle/wrapper/**`, `gradlew` | 물어봄 | 실행 권한·버전이 CI 를 깨뜨린다 |
| `config/checkstyle/**`, ArchUnit 규칙 | 물어봄 | **게이트를 낮춰서 초록불을 만드는 우회로** |
| `docs/wiki/**` | 금지 | 서브모듈. 여기서 고치면 detached HEAD 커밋이 되어 사라진다 |

마지막 줄이 백엔드에만 있는 항목이다. 게이트가 막으면 에이전트에게는 두 갈래가
있다. 코드를 고치거나, **규칙을 고치는 것.** 후자가 훨씬 쉽고 diff 도 작다.
규칙 파일을 열어둔 채로는 게이트가 게이트가 아니다.

### 왜 두 겹인가

`permissions.deny` 의 `Edit(...)` 규칙은 **Edit 도구만 본다.** 문제는 Bash 다.

```bash
sed -i '' 's/error/warning/' config/checkstyle/checkstyle.xml
cat > .githooks/prepare-commit-msg
git checkout main -- .github/workflows/ci-cd.yml
```

그래서 PreToolUse 훅으로 그 문을 닫는다. 보호 경로와 쓰기 표현이 같이 나오면
막고 읽기는 통과시킨다. 프론트의 `guard-shared.mjs` 와 같은 구조이고, 보호
목록에 규칙 파일이 더해진다.

**이것도 완전하지 않다.** 쓰기를 표현하는 방법은 무한하고 훅에 적힌 패턴은
유한하다. 훅은 로컬이라 끌 수도 있다. 그래서 백엔드에서는 프론트와 달리 **아래
한 겹을 더 깐다.**

### CODEOWNERS 는 공용 부진만 잡는다

역할 분담(어느 도메인을 누가 맡는가)은 아직 팀과 합의되지 않았다. 그래서
도메인 패키지에 소유자를 박지 않는다. 박아두면 정해지지 않은 경계를 도구가
먼저 정해버리고, 병렬 작업이 승인 대기로 막힌다.

**지금 소유자를 박는 것은 셋 다 밟게 되는 공용 부진뿐이다.** 위 "손대면 안 되는
곳" 표의 경로와 게이트 규칙 파일이다. 도메인은 열어둔다. 역할 분담이 정해지면
그때 도메인별로 넓힌다.

```bash

cd duckmoim-backend
./gradlew build                # 커밋 훅과 위키 서브모듈이 여기서 켜진다
git config core.hooksPath      # .githooks 가 나와야 한다
ls docs/wiki                   # 비어 있으면 위키 접근 권한을 받아야 한다
```

`--recurse-submodules` 를 빼먹어도 `./gradlew build` 가 `initWiki` 로 채운다.
**실패하면 경고가 찍힌다** — 조용히 넘어가지 않는다.

읽는 순서는 `CLAUDE.md` 의 작업 규칙, 그리고 위키 04-협업-규칙의 컨벤션 넷이다.
컨벤션 중 게이트가 검사하는 항목은 위 표에 있다. **표에 없는 항목이 리뷰에서
지적되는 것들이다.**
