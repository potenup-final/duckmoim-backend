# 테스트

**커버리지 목표 수치를 두지 않는다.** 대신 아래 네 가지는 없으면 리뷰에서 반려된다.

| 분류 | 대상 | 방식 |
|---|---|---|
| 동시성 | 유니크 제약, 카운트 증가, 정원 제한 | 통합 테스트 + 멀티스레드 |
| 권한 판정 | 요청자에 따라 결과가 달라지는 로직 | **모든 조합** |
| 상태 전이 | 허용된 전이와 **금지된 전이 모두** | 단위 테스트 |
| 멱등성·경계 | 재실행, 커서 페이지네이션 경계 | 통합 테스트 |

**테스트 목록은 요구사항 명세의 검증 기준이다.** 별도로 설계하지 않는다.
`docs/wiki/01-제품-요구사항/1차-MVP-기능-명세서.md` 2장의 마지막 열.

- 메서드명은 영어. 실패 케이스는 `{메서드명}_{실패이유}` (`pay_pointIsNotEnough`)
- `@DisplayName` 은 사용자 행위·비즈니스 규칙 중심, 어투는 `~다.` 로 통일
- given·when·then 으로 나누고 **when 은 한 번만** 실행한다. 두 번 나오면 테스트를 나눈다
- 예외 검증은 `assertThatThrownBy` 로 하고 **타입만 보지 말고 `ErrorCode` 까지** 본다
- 응답에서 필드를 제거하는 요구사항은 **값이 null 인지가 아니라 키가 없는지**를 검증한다
- 커서 페이지네이션은 정렬 키가 같은 데이터를 일부러 만들어 경계를 본다
- **동시성 테스트에 `@Transactional` 을 쓰지 않는다.** 별도 스레드는 테스트의
  트랜잭션에 참여하지 않아서, 롤백을 걸면 테스트가 **항상 통과하는 상태**가 된다
- **H2 를 쓰지 않는다.** 제약 위반 예외와 락 동작이 운영 DB 와 다르다

게이트가 검사하는 것 — Checkstyle 메서드 네이밍 · ArchUnit `TEST_HAS_DISPLAY_NAME`.

`src/test/java/com/duckmoim/architecture/` 는 **게이트 규칙 자체**다. 손대기 전에
물어본다. 규칙을 추가하면 `RulesAreAliveTest` 에 생존 증명도 같이 추가한다.
