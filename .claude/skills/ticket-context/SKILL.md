# 티켓 컨텍스트 확보

루프의 [1]이다. **산출물은 이 티켓이 통과해야 하는 테스트 목록 하나.**

테스트 컨벤션이 *"요구사항 명세의 검증 기준이 곧 테스트 목록이다. 별도로 테스트
케이스를 설계하지 않는다"* 라고 못박았다. **창작이 아니라 수집이다.**

그리고 이 단계의 진짜 목적은 이것이다 — **모르는 것을 채우는 것이 아니라, 기본값으로
알고 있는 것을 덮어쓰는 것.** 일반적인 모범 사례가 이 프로젝트에서 이미 기각된
경우가 있다. 그걸 모르고 "일반적으로 맞는" 코드를 자신 있게 쓰는 것이 이 단계를
건너뛴 대가다.

## 0. 위키를 최신으로 맞추고 기준선을 적는다

```bash
git submodule update --init --remote docs/wiki && ls docs/wiki/README.md
git -C docs/wiki rev-parse HEAD > .git/wiki-seen-sha   # 기준선
```

세션 시작 훅이 이미 한 번 맞췄다. 그래도 **여기서 다시 한다** — 위키를 실제로 읽는
순간은 여기이고, 세션이 몇 시간 가는 동안 위키가 바뀔 수 있다. 이미 최신이면 1초
안에 끝난다.

- 실패하고 `docs/wiki` 가 **비어 있으면 멈추고 사람에게 알린다.** 스펙 없이 구현하지
  않는다. 위키는 PRIVATE 이라 접근 권한이 필요할 수 있다
- 낡은 사본이라도 있으면 진행하되, **인용할 때 최신이 아닐 수 있음을 밝힌다**
- `.gitmodules` 가 아예 없으면 이 브랜치가 하네스 머지 전에 갈라진 것이다.
  `git rebase origin/develop` 이 필요하다고 알린다

**둘째 줄이 기준선이다 — 이 티켓이 어느 판본을 읽었는지.** `syncWiki` 가 매 빌드마다
위키를 최신으로 당기므로, [3] 구현과 [4] `check` 를 오가는 사이에 누가 위키를 고치면
**디스크만 조용히 바뀐다.** 컨텍스트는 여기서 읽은 판본 그대로라 갈라진 줄 모르고
옛 내용을 인용하게 된다. 기준선이 있으면 `syncWiki` 가 [4] 출력에 무엇이 바뀌었는지
찍어준다.

`.git/` 아래라 커밋되지 않고 `clean` 에도 안 지워진다. **기준선이 없으면 아무 경고도
안 나온다** — 이 줄을 건너뛰면 감지 자체가 꺼진다.

경고가 뜨면 바뀐 문서의 해당 절을 다시 읽고, [2] 에 올린 계획이 걸리면 계획부터
고친 다음 기준선을 갱신한다.

```bash
git -C docs/wiki rev-parse HEAD > .git/wiki-seen-sha
```

**갱신 전까지 경고는 계속 뜬다.** 한 번만 알리면 출력이 밀려 올라간 사이에 놓친다.

읽은 판본은 [2] 계획과 PR 본문에도 적는다 (`위키 87d25e5` 한 줄). 리뷰어가 어느
계약을 보고 짠 코드인지 알 수 있어야 한다.

## 1. 요구사항 ID 를 확정한다

**ID 는 티켓 제목에 있다.** 지라 제목이 GitHub 이슈 제목으로 그대로 넘어온다.

```bash
key=$(git branch --show-current | sed -nE 's#.*/([A-Z]+-[0-9]+)$#\1#p')
gh issue list --state all --search "\"[$key]\" in:title" --json title --jq '.[0].title'
```

| 제목 | 뽑히는 ID |
| --- | --- |
| `[STAR-40] feat: AU-06 소셜 로그인` | `AU-06` |
| `[STAR-29] chore: EV-01~04 행사 데이터 이관` | `EV-01` `EV-02` `EV-03` `EV-04` |
| `[STAR-36] fix: 에이전트 루프용 하네스 수정` | 없음 |

**ID 가 없을 때의 판정은 접두어로 한다.**

| 접두어 | ID 가 없으면 |
| --- | --- |
| `feat` · `fix` | **멈추고 사람에게 묻는다.** 추측하지 않는다 |
| `chore` · `docs` · `test` · `refactor` | 그대로 진행한다. 요구사항을 구현하지 않는 티켓이 실재한다 (#6, #11) |
| **없음** | **묻는다.** 지라 제목에 접두어가 빠진 티켓이 실재하고 (`[STAR-30] 전역 예외 처리 구현`), 그때는 요구사항 티켓인지 판별할 근거가 없다 |

ID 접두어가 소속 문서를 정한다. `docs/wiki/README.md` 의 **ID 체계** 표에 있다.

## 2. 이 티켓의 정본을 확정한다

**문서 둘이 다르게 적혀 있을 때 어느 쪽을 따르는지가 먼저다.** 이걸 안 정하고
훑기 시작하면 어긋난 자리에서 그때그때 판단하게 되고, 그 판단은 근거가 없다.

| 영역 | 정본 | 살아 있는 출처 |
| --- | --- | --- |
| 요구사항 · 검증 기준 · 우선순위 | 1차 MVP 기능 명세서 | `docs/wiki/README.md` 「ID 체계」 |
| 불변식 · 애그리게이트 · 용어 | 도메인 모델링 | 같은 표 |
| 엔드포인트 · 권한 · 응답 필드 | API 설계 | 화면 계약 「어느 것이 정본인가」 |
| **행사(Catalog) 필드 · 값 집합 · 열거값** | **화면 계약 1장** | 화면 계약 「어느 것이 정본인가」 · `02-설계-아키텍처/README.md` · 도메인 4.1 |
| 봉투 · 표기 · 에러 형식 | API 컨벤션 | 화면 계약 0장 |

**행사만 반대 방향이다.** 크롤러 · 프론트 · 백엔드 셋이 같은 필드를 쓰는데, 셋 중
하나의 코드를 정본으로 삼으면 나머지 둘은 베끼는 처지가 되고 베낀 것은 반드시
갈라진다. 그래서 계약이 코드가 아니라 문서에 있다. **`types.ts` 와 다르다는 것은
문서의 결함이 아니라 구현이 밀린 상태다.**

`EV-` 티켓이면 화면 계약 1장을 **가장 먼저** 읽는다. 그 밖의 영역에서 화면 계약은
화면 쪽 요구사항일 뿐이고, API 설계와 어긋나면 API 설계가 이긴다.

정본이 정한 값과 게이트 규칙이 반대이면 **규칙이 틀린 것이다.** 코드를 비틀어
맞추지 않는다 — `CLAUDE.md` 「게이트가 무엇을 보는가」를 따른다.

## 3. 여섯 곳을 훑는다

ID 하나당 여섯 군데를 본다. **한 곳만 보면 절반만 안다.**

```bash
ID=AU-06   # 예시

# ① 검증 기준 — 표의 마지막 열이 곧 테스트 목록이다
grep -n "$ID" docs/wiki/01-제품-요구사항/1차-MVP-기능-명세서.md

# ② 불변식 — 그 요구사항을 인용하는 I-nn 을 찾는다.
#    검증 위치와 이중 방어가 여기에만 적혀 있다
grep -n "$ID" docs/wiki/02-설계-아키텍처/도메인-모델링.md

# ③ 유비쿼터스 언어 — 쓸 식별자를 여기서 가져온다. 지어내지 않는다
sed -n '/## \*\*1. 유비쿼터스 언어/,/^---/p' docs/wiki/02-설계-아키텍처/도메인-모델링.md

# ④ 에러 코드 — 이미 20개가 근거 ID 까지 붙어 정해져 있다
grep -n "$ID" docs/wiki/02-설계-아키텍처/API-설계.md

# ⑤ 설계 결정 — 가장 안 찾아보면서 피해가 크다
sed -n '/## 5. 결정 사항/,/## 6./p' docs/wiki/02-설계-아키텍처/API-설계.md
ls docs/wiki/02-설계-아키텍처/ADR/

# ⑥ 화면 계약 — 행사(EV)는 여기가 정본이다. EV- 티켓이면 ① 보다 먼저 읽는다
grep -n "$ID" docs/wiki/02-설계-아키텍처/화면-계약.md
sed -n '/^## 1. 행사 (EV)/,/^## 2\./p' docs/wiki/02-설계-아키텍처/화면-계약.md
```

⑥ 은 **필드 이름 · 타입 · 열거값 · 필수 여부**를 정한다. 행사에서는 여기 적힌 것이
계약이고, `types.ts` 나 기존 응답 코드와 달라도 이쪽이 이긴다 (2절).

**`EV-` 는 grep 이 비어도 정상이다.** 1장 전체가 행사 계약이라 개별 요구사항 ID 를
달지 않는다 (`EV-05` · `EV-06` 이 그렇다). 비었다고 「화면 계약에 없다」로 읽지 말고
`sed` 로 1장을 통째로 읽는다.

②에서 `I-nn` 을 찾으면 **그 불변식 행을 다시 읽는다.** `검증 위치` 가 코드를
어디에 놓을지 결정하고, `이중 방어` 가 테스트 계층을 결정한다.

| 이중 방어 | 테스트 |
|---|---|
| DB 유니크 제약 · 체크 제약 | **통합 테스트.** 멀티스레드. `@Transactional` 금지 |
| 없음 (`—`) | 단위 테스트로 충분 |

②에서 검증 위치가 **미정**으로 적혀 있으면 5장의 「확인이 남은 것」을 읽고
**사람에게 결정을 요청한다.** 추측해서 만들면 없는 합의를 있는 것처럼 굳힌다.

**무엇이 미결인지는 그 절을 읽어서 안다. 여기 적힌 목록을 믿지 않는다.** 한때
`I-04` · `I-14` 가 미정이었는데 2026-09-05 회의에서 결정됐다 — `I-04` 는 이중 방어를
두지 않고, `I-14` 는 정책 객체다. 지금 남은 것은 신고 처리 **결과**의 표현 하나이고
(상태 `PENDING` · `PROCESSING` · `RESOLVED` 는 확정), 이것도 곧 바뀐다.

## 4. 테스트 목록으로 옮긴다

검증 기준 한 줄이 `@DisplayName` 한 개다.

```
AU-06  동시 요청 2건 중 1건만 성공, 나머지 409
  → @DisplayName("동일 닉네임으로 동시 가입하면 한 건만 성공한다.")
     통합 테스트 + 멀티스레드 (I-01 의 이중 방어가 DB 유니크 제약)

CM-12  동시 작성 100건 후 카운트 정확
  → @DisplayName("댓글 100건을 동시에 작성해도 집계가 정확하다.")
     통합 테스트. 저장하지 않고 조회 시 세는 구조라 저장값 불일치는 없다
```

권한 판정이 걸리면 **모든 조합**을 낸다. 조건이 셋 이상이면 `@ParameterizedTest`.
대표 케이스만 고르지 않는다.

## 5. 사람에게 보고할 것

수집이 끝나면 구현에 들어가기 전에 아래를 요약한다.

- **이 티켓의 정본** (2절 판정 결과). 특히 행사를 건드리면 화면 계약 1장이라는 것
- 요구사항 ID 와 검증 기준 개수
- 뽑아낸 테스트 목록 (`@DisplayName` 초안)
- 쓸 식별자 (유비쿼터스 언어에서 가져온 것)
- 재사용할 에러 코드, 새로 만들어야 하는 것
- **걸리는 설계 결정** — 특히 일반적인 방식과 다른 것
- **막힌 것** — 미정인 검증 위치, 문서에 없는 값 (환경변수 이름 · CORS 오리진 등)

마지막 항목이 비어 있지 않으면 **그것부터 사람에게 묻는다.** 문서에 없는 것을
지어내면 셋이 각자 다르게 지어낸다.
